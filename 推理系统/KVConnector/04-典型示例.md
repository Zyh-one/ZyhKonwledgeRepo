# 04 · 典型示例

> 本篇挑两个代表 Connector，把 [03-工作原理](./03-工作原理-KVConnectorBase_V1.md) 的接口时序走通：MooncakeConnector 做 PD Transfer，OffloadingConnector 做 Device↔CPU 二级 Cache。其余 Connector 用简表给出定位，细节交回各自子页。

## 4.1 MooncakeConnector：Prefill → Decode P2P 交接

### 定位

`MooncakeConnector` 用于 Prefill 与 Decode 之间的**点对点 KV Transfer**，role 上 Prefill = `kv_producer`、Decode = `kv_consumer`，数据面走 Mooncake Transfer Engine（RDMA）。它不涉及"历史 Prefix 复用"，只解决"当前请求 Prompt KV 怎么从 P 送到 D"。

> Mooncake Transfer Engine 的工程细节（启动参数、带宽、源码位置）见 [`../其他细节/PD分离/MoonCake/MoonCake_transfer_engine.md`](../其他细节/PD分离/MoonCake/MoonCake_transfer_engine.md)。

### 端到端时序

```
Prefill 实例 (producer)                         Decode 实例 (consumer)
──────────────────────                          ──────────────────────
① on_new_request(req)
② get_num_new_matched_tokens()
   → 命中本地/外部前缀后算剩余
③ Prefill 计算，逐层：
     save_kv_layer(layer)   ──┐
     # 算完即异步 RDMA 写出     │ KV blocks
                              ├─ P2P / RDMA ──────────────▶  bind_connector_metadata()
     wait_for_save()         ─┘                              start_load_kv()
④ request_finished(req)                                      wait_for_layer_load(layer)
   → defer=True，异步发送完成前                              # 逐层等 KV 到位后 decode
   block 不释放
⑤ get_finished() 上报 sending 完成                            get_finished() 上报 recving 完成
   → has_pending_block_frees() 释放                          → 接收完整后开始 autoregressive decode
```

关键点：
- **发送时机**：`save_kv_layer` 在 Prefill 的 attention 层内调用，算完一层就异步 RDMA 写出，与计算 overlap；
- **可靠送达**：producer 侧 `requires_kv_delivery=True`，`request_finished` 返回 defer，KV 未发完前 block 不被覆盖；
- **Decode 侧阻塞**：`wait_for_layer_load` 在 Decode 的 attention 层内逐层阻塞，等对应 KV 到位才算；
- **握手**：`get_handshake_metadata` / `build_connector_worker_meta` 负责 P/D worker 间带外握手，让 consumer 知道哪些 block 在远端、地址如何映射。

### 拆源码要回答的问题

1. Scheduler 如何知道某请求需要 remote KV？
2. Prefill 如何通知 Decode KV 已就绪？
3. KV block 如何映射到远端地址？
4. 数据面什么时候开始 RDMA？
5. transfer 完成信号如何反馈 Scheduler？
6. 请求 abort 后 KV 如何清理？

> 这套时序与 PD 分离整体链路的关系，见 [`../其他细节/PD分离/KVCache传输.md`](../其他细节/PD分离/KVCache传输.md) 的"点对点传输"模式。

## 4.2 OffloadingConnector：Device ↔ CPU 二级 Cache

### 定位

`OffloadingConnector` 把已完成 KV block 扩展到 CPU（`CPUOffloadingSpec`）或可选二级 Tier（`TieringOffloadingSpec`），本质是**构建一个比设备 KV Cache 更大的 External Prefix Cache**。它解决的是 [02-基本概念](./02-基本概念.md) 里的 KVOffload，不是请求抢占。

### Store / Load 时序

**Store（Device → CPU，Eager 模式）**

```
① 请求 Prefill 计算，逐层：
     save_kv_layer(layer)        # 算完即异步拷到 CPU
     wait_for_save()             # forward 退出，等拷完
② request_finished(req) → defer=True
   # 异步保存完成前 block 不释放
③ has_pending_block_frees() → 释放
```

**Load（CPU → Device，Hit-driven）**

```
① get_num_new_matched_tokens(req)
   → (external_hit_tokens, is_async)   # 查到外部命中多少
② update_state_after_alloc(req, blocks, external_hit_tokens)
   # 决定加载哪些 block
③ build_connector_meta → metadata 下发
④ Worker: bind_connector_metadata()
⑤ start_load_kv()                # 启动 CPU→Device 加载
⑥ 逐层: wait_for_layer_load()    # 等本层加载完再算
⑦ 只计算未命中 token
```

### 为什么 Store Bytes ≫ Load Bytes

```
新 Prompt 被计算 → 很多 KV block 被 Store → MLU→CPU = 900 GB
未来真正被重复请求的只一部分 → External Prefix Hit → CPU→MLU = 88 GB
```

写进 Cache 的 KV 不代表未来一定被命中，所以 `Store >> Load` 是正常 Cache 行为，不是异常。

### 监控指标对应

| 指标 | 对应动作 |
|---|---|
| `external_prefix_cache_hits` | `get_num_new_matched_tokens` 命中的外部 token 数 |
| KV Offload `CPU→Device` bytes | `start_load_kv` 触发的 Load |
| KV Offload `Device→CPU` bytes | `save_kv_layer` 触发的 Store |
| `num_preemptions` | Scheduler 抢占，**与 Offload 独立** |

可用 `CPU_to_Device_bytes / external_hit_tokens ≈ KV_bytes_per_token` 验证 `Lookup → Hit → Load` 链路自洽。

### MLU 注意

upstream OffloadingConnector 官方支持 CUDA / ROCm / XPU。线上看到 `vllm:kv_offload_total_bytes_total{transfer_type="MLU_to_CPU"}` 很可能含寒武纪侧适配。拆源码应优先在 vLLM-MLU 分支找 `kv_offload_total_bytes_total.inc(...)` 的真实调用点，而非照 upstream 猜触发条件。

## 4.3 其余 Connector 简表

| Connector | 定位 | 细节子页 |
|---|---|---|
| **MooncakeStoreConnector** | 用 Mooncake Distributed Store 做跨实例共享 External Prefix Cache（PUT/GET/LOOKUP），可与 MooncakeConnector 经 MultiConnector 组合，同时得到 P→D Transfer + 共享 Prefix Cache | — |
| **LMCacheConnectorV1 / LMCacheMPConnector** | KV Cache 中间件，多级（CPU/Disk/分布式）缓存、跨实例共享、PD transport；MP 模式接独立 LMCache Server，是"KV Cache 服务化"的学习对象 | — |
| **NixlPullConnector / NixlPushConnector** | 高性能异步 PD KV Transfer 抽象，READ/Pull 与 WRITE/Push 两种风格，底层 RDMA/UCX/GDS，零/少拷贝 | [`../其他细节/PD分离/Nixl/Nixl握手.md`](../其他细节/PD分离/Nixl/Nixl握手.md) |
| **FlexKVConnectorV1** | 大规模分布式 KV Store / 多级 Cache | — |
| **MultiConnector** | 组合多种正交 KV 能力（见 [03 §3.6](./03-工作原理-KVConnectorBase_V1.md)） | — |

> MooncakeStore / LMCache / FlexKV 在本仓库暂无独立子页，后续拆源码时可在此扩展或新建。

## 4.4 三种 Connector 能力的组合关系

```
                         Prefill
                            │
           ┌────────────────┴────────────────┐
           │                                 │
   External Prefix Cache               Current Request KV
   (MooncakeStore / Offloading)               │
           │                                 │
      CPU Store ↔ Load                         │
        (Device↔CPU)                           │
           │                                 │
           └──────────→ Prefill ─────────────┘
                                      │
                                      │ PD KV Transfer (Mooncake / NIXL)
                                      ▼
                                    Decode
                                      ├─ 接收 Prompt KV
                                      └─ Autoregressive Decode
```

左边 CPU↔设备 解决**历史 Prefix KV 的保存与复用**；右边 Prefill→Decode 解决**当前请求 Prompt KV 的跨实例交接**。两条路径可由不同 Connector 完成，也可借 `MultiConnector` 组合。
