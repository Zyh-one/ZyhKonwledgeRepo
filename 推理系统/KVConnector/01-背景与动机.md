# 01 · 背景与动机

> 回答"为什么会有 KVConnector 这层抽象"。先看 KV Cache 本身的成本压力，再看 vLLM V0 时代零散的传输方案，最后看 V1 为什么需要统一。

## 1.1 LLM 推理的访存墙与 KV Cache 成本

Transformer 自回归推理有两个特征截然不同的阶段：

- **Prefill**：一次处理完整输入序列，矩阵规模大，偏**计算密集型**，直接决定 TTFT；
- **Decode**：每轮只生成一个 token，但要反复读取模型权重和 KV Cache，偏**访存密集型**，直接决定 TPOT。

随着上下文变长（几十 K 到上百 K token），**KV Cache 而非模型权重** 成了显存和带宽的主要开销。粗略地说：

```
KV Cache 大小 ≈ num_layers × 2 (K+V) × num_kv_heads × head_dim × seq_len × dtype_bytes
```

一个 70B 级模型、长上下文场景下，单请求 KV Cache 可达数十 GB 量级。这带来三个直接诉求：

1. **KV Cache 需要能跨请求复用**——相同 system prompt 不该重算；
2. **KV Cache 需要能跨层级搬运**——设备 HBM 放不下时，要有 CPU / DRAM / SSD 等更大更慢的 Cache Tier；
3. **KV Cache 需要能跨实例交接**——Prefill 和 Decode 拆到不同实例时，Prompt KV 要从 P 节点送到 D 节点。

KVConnector 就是为这三件事提供统一接口的抽象层。

## 1.2 V0 时代：零散的 KV 传输

vLLM V0 时代并没有一个统一的 KV Cache 数据面抽象。跨实例 KV 传输是**各家自带、接口各异**的：

| V0 Connector | 思路 | 局限 |
|---|---|---|
| **PyNcclConnector** | 用 NCCL 在 P/D 实例间收发 KV | 接口围绕"整次传输"，不表达查询命中 / 多级 Cache |
| **LMCacheConnector** | 接 LMCache 中间件做 CPU/Disk 多级缓存 | 与传输耦合不深，命中与搬运语义自成一派 |
| **SHarpConnector (BSHarp)** | 通过 InfiniStore 做 P2P | 传输时机依赖 **decode 阶段发 dummy token** 来"挤"出 KV，非常 hacky |

V0 的核心问题是：**"查询命中 / 加载 / 保存 / 跨实例交接"这四组能力是正交的，但旧接口把它们焊死在各自实现里。** 想同时做"PD 交接 + 跨实例 Prefix 复用 + CPU 二级 Cache"，只能在一个 Connector 里堆逻辑，无法组合。

## 1.3 统一诉求：Disaggregated Serving + 跨实例 Prefix 复用

两股力量把"统一 KV 数据面"从锦上添花变成刚需：

**力量一：Disaggregated Serving 成为主流方向。**

DistServe（OSDI'24）、Splitwise 等工作指出，Prefill 和 Decode 混合部署会相互干扰、且最优资源配置不同，应拆到独立实例。拆开后的代价就是 **KV Cache 必须跨实例传输**——长上下文下通信开销尤其明显。PD 分离的收益能否覆盖传输成本，直接取决于 KV 数据面的效率。

> PD 分离的工程细节见 [`../其他细节/PD分离/PD分离.md`](../其他细节/PD分离/PD分离.md)。

**力量二：跨实例 Prefix Cache 复用。**

同一个 system prompt（或长前缀）被不同实例、不同请求反复使用。如果 KV Cache 只能待在算它的那块卡上，复用就只能靠本地命中。要把它变成**跨实例共享的 External Prefix Cache**，就需要一个统一的查询 + 搬运接口，并且让"KV 放在哪"和"谁来传"解耦。

## 1.4 V1 的解法：KVConnectorBase_V1 统一抽象

vLLM V1 引入 [`KVConnectorBase_V1`](./03-工作原理-KVConnectorBase_V1.md)，把数据面拆成两个职责清晰的侧面：

```
   Scheduler 侧                          Worker 侧
   ─────────────                         ─────────────
   查什么 / 命中多少 /                    真正搬运 KV：
   哪些 block 要 load/store              Load / Save / P2P Transfer
        │                                       │
        └────── KVConnectorMetadata ───────────┘
                 （Scheduler 下发给 Worker）
```

它的设计要点：

1. **Scheduler 决策、Worker 搬运分离**——Scheduler 通过 `get_num_new_matched_tokens()` 决定外部能命中多少，Worker 通过 `start_load_kv()` / `save_kv_layer()` 真正执行；
2. **接口正交、可组合**——`MultiConnector` 可以把 PD Transfer + External Cache + KVOffload 拼起来，而不是塞进一个 Connector；
3. **异步逐层流水线**——`save_kv_layer()` 在 attention 层内调用以支持计算与拷贝 overlap，`wait_for_layer_load()` 逐层阻塞；
4. **CUDA graph 兼容**——异步逐层操作时通过 `requires_piecewise_for_cudagraph` 启用 piecewise graph，避免重放竞争。

## 1.5 小结：KVConnector 解决的本质问题

一句话：

> **KVConnector 把"KV Cache 放在哪、谁来命中、怎么搬运"从各家实现里抽出来，变成 vLLM Core 与外部 KV 系统之间的一组统一接口。**

它不是某一个传输后端，而是让 Mooncake / NIXL / LMCache / Offloading 等后端都能以同一套 Scheduler/Worker 钩子接入 vLLM 的契约。理解了这一点，再去看具体 Connector 就是"看某个后端如何实现这套契约"，而不是"学一套新机制"。
