# 02 · 基本概念

> 把 KVConnector 体系里反复出现的术语对齐。本篇只做最小铺垫，PagedAttention / PrefixCache 的深度展开见各自子页。

## 2.1 KV Cache

Transformer 自回归生成依赖前面所有 token 的 K、V。为避免每生成一个 token 就重算整段历史，推理引擎会把每层的 K、V 缓存下来，这就是 **KV Cache**。

- 它随序列长度线性增长，长上下文下是显存大头；
- 它的存在让 Decode 从"重算全序列"退化成"读 KV + 算一个 token"，是把 Decode 变成访存密集型的根本原因。

> PagedAttention 如何用 block 粒度组织 KV Cache，见 [`../其他细节/PagedAttention.md`](../其他细节/PagedAttention.md)。

## 2.2 Block / Chunk 粒度与 Block Hash

vLLM 用 PagedAttention 把 KV Cache 切成固定大小的 **block**（通常 16 token 一块）。Prefix 匹配以 block 为粒度：

```
token sequence
    ↓
按 block 切分
    ↓
对每个 block 的 token 序列做 hash
    ↓
hash 作为 KV block 的 Key
```

因此 Prefix 命中本质是 **"这段前缀的 block hash 链，我以前算过吗"**。这是 Local 与 External Prefix Cache 共用的匹配逻辑，只是 KV 数据落点不同。

> Prefix Cache 的深度展开见 [`../其他细节/PrefixCache.md`](../其他细节/PrefixCache.md)。

## 2.3 Local Prefix Cache vs External Prefix Cache

| | Local Prefix Cache | External Prefix Cache |
|---|---|---|
| KV 落点 | 当前 vLLM 实例自己的设备 KV Cache | 外部（CPU / 远端 DRAM / SSD / 分布式 Store） |
| 命中后 | 直接复用，无跨设备传输 | 命中后需把 KV **加载**回设备 |
| 查询入口 | vLLM 内部 block pool | KVConnector 的 `get_num_new_matched_tokens()` |

二者不是两套算法，而是同一套 hash 匹配在**不同存储位置**上的两层。一次请求的命中流程是：

```
Request
   ↓
Local Prefix Cache Lookup ── 本地命中部分
   ↓ (本地未命中部分)
KVConnector External Lookup ── 外部额外命中部分
   ↓
Load External KV ── 只计算剩余未命中 token
```

所以 `external_prefix_cache_hits` 表示的是**从外部 KV Cache 额外命中的 token 数量**，不是"命中了多少次请求"。

## 2.4 KVOffload：二级 Cache 语义（≠ 旧 Swap / 抢占）

这是最易混淆的一点，必须切开。

**旧语义：Swap / Preemption**

```
设备 KV Cache 不足 → Scheduler 抢占请求 → 把请求 KV 搬到 CPU → 以后再恢复
```

这是资源压力驱动的请求级抢占。

**现代语义：KVOffload（二级 KV Cache）**

```
设备计算完成的 KV Block → Store 到更大更慢的 Cache Tier (CPU)
未来 Prefix 再次命中 → Load 回设备
```

KVOffload 更像在主动构建一个**更大的 External Prefix Cache**，与请求抢占没有必然关系。因此线上完全可能出现：

```
MLU → CPU = 几百 GB
num_preemptions = 0
```

二者并不矛盾。`Offload Bytes > 0` 不等于发生了 Request Preemption。

### Store / Load 的触发模式

KVOffload 什么时候搬 KV，由 Connector 实现和策略决定，常见有：

- **Eager / Produce-time Store**：KV block 计算完成就存到 CPU，不要求设备 KV Cache 不足——主动建 Cache；
- **Lazy / Eviction-oriented Store**：block 接近从设备 Cache 淘汰时才 offload——与内存压力相关，但仍不等于请求级抢占；
- **Hit-driven Load**：请求来了 → 外部 lookup → 命中 → 分配设备 block → CPU→Device 加载。

这也是为什么线上常观察到 `External Prefix Hit 曲线 ≈ CPU→Device Bytes 曲线`：固定模型/TP/KV dtype 时近似有 `CPU_to_Device_bytes ≈ external_hit_tokens × KV_bytes_per_token`。

## 2.5 PD Transfer：当前请求 KV 的跨实例交接

PD 分离把 Prefill 和 Decode 放到不同实例。请求的 Prompt KV 在 Prefill 算完后，要交给 Decode 继续生成。KVConnector 在这里充当 **KV Producer → KV Consumer** 的传输层：

```
Client → Router → Prefill (kv_producer)
                        │ 计算 Prompt KV
                        ▼
                   KVConnector ── P2P / RDMA ──▶ Decode (kv_consumer)
                                                   │ 接收 Prompt KV
                                                   ▼
                                                生成 Token
```

注意区分它与 KVOffload 的数据路径：

| | KVOffload（CPU↔设备） | PD Transfer（P→D） |
|---|---|---|
| 解决 | 历史 Prefix KV 的保存与复用 | 当前请求 Prompt KV 的跨实例交接 |
| 方向 | 设备 ↔ CPU/外部 Tier | Prefill → Decode |
| 时间 | 跨请求、跨生命周期 | 当前请求生命周期内 |

两条路径可能同时存在，并可由不同 Connector 完成、或借助 `MultiConnector` 组合。

> PD 分离与传输模式细节见 [`../其他细节/PD分离/PD分离.md`](../其他细节/PD分离/PD分离.md) 与 [`../其他细节/PD分离/KVCache传输.md`](../其他细节/PD分离/KVCache传输.md)。

## 2.6 三者关系：围绕 KVConnector 串起

```
                         ┌─────────────┐
                         │   Request   │
                         └──────┬──────┘
                                ▼
                    ┌─────────────────────┐
                    │  Local Prefix Cache  │
                    └──────────┬──────────┘
                               │ miss
                               ▼
                    ┌─────────────────────┐
                    │     KVConnector     │
                    └───┬─────────────┬───┘
            External Ck │             │ PD Transfer
                        ▼             ▼
              ┌──────────────┐  ┌────────────────┐
              │ CPU / Store  │  │  Prefill → D   │
              └──────┬───────┘  └────────────────┘
            Store ↔ Load
            (Device↔CPU)
```

- **External Prefix Cache** = 复用（"以前算过的能不能用"）
- **KVOffload** = 搬运与分层（"可复用的 KV 放哪、怎么搬"）
- **PD Transfer** = 交接（"当前请求的 KV 怎么从 P 给 D"）

三者各自正交，但都通过 `KVConnectorBase_V1` 的同一套 Scheduler/Worker 接口实现。下一篇 [03-工作原理](./03-工作原理-KVConnectorBase_V1.md) 下沉到这层接口。
