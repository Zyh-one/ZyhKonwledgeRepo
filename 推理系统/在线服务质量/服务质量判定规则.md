# 在线 LLMServing 服务质量判定规则

- **适用范围**：黄曲生产集群 namespace `ns-e23f5b20fb9b42d3ac674f9691a0b9b1` 下，ai-coding 智能路由所辖在线 LLMServing
- **当前目标服务**：`deepseek-v4-dp2tp4`、`glm52-8-pd`
- **数据来源**：VMSelect（VictoriaMetrics 集群，`/select/0/prometheus/api/v1/...`，vmselect-node-port 172.26.254.216:8481）
- **取数方式**：只读 PromQL 查询，全程零变更
- **版本**：v0.1（初版，SLO 阈值待按真实分布细调）

---

## 一、服务质量定义

一个在线 LLMServing 的服务质量 = 在观察日内，该服务在 **可用性、延迟体验、吞吐能力、推理质量、资源效率、稳定性** 六个维度上相对既定 SLO 的达成程度，聚合为一个可比较的状态评价。

每维度判定为四态：
- 🟢 达标
- 🟡 临界
- 🔴 不达标
- ⚪ 未接入（指标暂缺，不影响其它维度判定）

**整体判定 = 短板原则**：取所有维度中最差者；可用性或稳定性任一为 🔴，则整体直接 🔴。

---

## 二、各维度判定规则

### 维度 1 · 可用性 Availability

**取数**：
- `num_requests_running` 当日峰值 > 0（有活流量）
- `engine_sleep_state`（是否休眠）
- LLMServing `.status.overview == Available` 当日时长占比（来自 kubectl 只读查询）

**判定**：
- 🟢 在线时长占比 ≥ 99% 且有持续流量
- 🟡 95% ≤ 占比 < 99%
- 🔴 占比 < 95%，或出现 Stopped/Expired

---

### 维度 2 · 延迟体验 Latency（主标尺：p95）

**取数**（24h，按 `exported_namespace` + `roleset=~"<SERV>-.*"` 过滤）：
```
TTFT_p95  = histogram_quantile(0.95, sum(increase(time_to_first_token_seconds_bucket{...}[24h])) by (le))
e2e_p95   = histogram_quantile(0.95, sum(increase(e2e_request_latency_seconds_bucket{...}[24h])) by (le))
queue_p95 = histogram_quantile(0.95, sum(increase(request_queue_time_seconds_bucket{...}[24h])) by (le))
```

**判定**（三项需同时达标，取最差）：
- 🟢 三项 p95 均 ≤ SLO
- 🟡 TTFT/e2e 任一超标但 p50 正常（尾部恶化，主体仍可接受）
- 🔴 TTFT 或 e2e 的 p95 超标且 p50 亦异常（主体体验已恶化）

---

### 维度 3 · 吞吐能力 Throughput

**取数**：
- `sum(increase(e2e_request_latency_seconds_count{...}[24h]))` —— 当日请求总量
- `max_over_time(num_requests_running{...}[24h])` —— 运行中峰值
- `max_over_time(num_requests_waiting{...}[24h])` —— 等待峰值
- `avg_over_time(avg_generation_throughput_toks_per_s{...}[24h])` —— 平均生成吞吐

**判定**（"是否过载"，非越高越好）：
- 🟢 `num_requests_waiting` 峰值 = 0 或仅瞬时 >0（无持续堆积）
- 🟡 waiting 持续 >0 但未长时间堆积（轻度过载）
- 🔴 waiting 长时间堆积（持续 N 分钟 > 阈值，N、阈值待定）

---

### 维度 4 · 推理质量 Quality（待接入）

**取数**：monitoring ns 的 `llm-accuracy-monitor`（ClusterIP 172.26.184.253:8080）。

**判定**：当前 ⚪ 未接入。接入后按准确率/异常输出占比阈值判定。

---

### 维度 5 · 资源效率 Efficiency（硬件为寒武纪 MLU）

**取数**（按 pod `namespace` + `pod=~"<SERV>-.*"` 过滤）：
```
MLU利用率均值  = avg(avg_over_time(application_container_mlu_utilization{...}[24h]))
MLU显存均值    = avg(avg_over_time(application_container_mlu_memory_utilization{...}[24h]))
KV cache峰值   = max_over_time(kv_cache_usage_perc{exported_namespace=...,roleset=~"<SERV>-.*"}[24h])
prefix cache命中率 = increase(prefix_cache_hits_total[24h]) / increase(prefix_cache_queries_total[24h])   （信息项）
```

**判定**：
- 🟢 MLU 利用率在 20–90%、显存 < 90%、kv_cache < 90%
- 🟡 MLU 利用率 < 20%（浪费）或显存 90–95%（偏高）
- 🔴 显存 ≥ 95%、或 kv_cache = 100%（过载风险）

---

### 维度 6 · 稳定性/故障 Stability（待补 MLU 错误指标）

**取数**（待补；NVIDIA 路径用 DCGM，MLU 路径缺等价指标）：
- NVIDIA：`increase(dcgm_xid_errors{...}[24h])`、`dcgm_gpu_health`、`dcgm_pcie_replay_counter`、`dcgm_gpu_temp`/`dcgm_memory_temp`
- MLU：待找错误/健康等价指标

**判定**：
- 🟢 当日无 XID/健康异常、无温度超限、无 OOM/重启
- 🟡 温度逼近阈值、 PCIe 重传偶发
- 🔴 XID 错误增量 > 0、或 health 异常、或 OOM/崩溃

## 三、SLO 阈值表（初版 v0.1）

| 服务 | TTFT p95 | e2e p95 | queue p95 | 可用性 | 错误率 | MLU 利用率 | MLU 显存 |
|---|---|---|---|---|---|---|---|
| `deepseek-v4-dp2tp4` | ≤ 5s | ≤ 60s | ≤ 10s | ≥ 99% | < 1% | 20–90% | < 90% |
| `glm52-8-pd` | ≤ 60s | ≤ 150s | ≤ 50s | ≥ 99% | < 1% | 20–90% | < 90% |

> **注（v0.1）**：初版阈值基于 7 天基线粗估，首跑（2026-09-28）实测 p95 远超阈值，判定偏严。后续按真实分布细调，或改为"达成率%"形式（如"95% 请求满足 TTFT ≤ X"）。

## 四、整体判定与报告输出

1. 六维度各自按上述规则给出 🟢/🟡/🔴/⚪。
2. 整体 = 最差维度（短板原则）；可用性、稳定性为 🔴 时整体直接 🔴。
3. 报告输出每日一份，落盘路径：`推理系统/在线服务质量/日报/服务质量日报_YYYY-MM-DD.md`。
4. 报告含：当日总览表、分服务明细表、一句话结论、SLO 对照、（可选）趋势。
