```
20:00 这个点是多少？
20:00:30 这个点是多少？
20:01:00 这个点是多少？
...
20:20:00 这个点是多少？
```

每个时间节点都重新执行同一条PromQL，PromQL的内部的时间数据都是始终围绕“这一次时间节点计算”的

# 1.CPU相关指标

## 1.2containerMemoryUsage

原始PromQL语句：

```
sum by(cluster,pod,container)(
  avg_over_time(
    container_memory_working_set_bytes{
      cluster=~"%(cluster)s",
      namespace="%(namespace)s",
      container=~"%(container)s",
      pod=~"%(pod)s"
    }[%(time)s:30s]
  )
)
```

* =~ 表示正则匹配；= 表示精确匹配
* [%(time)s:30s]：对应[时间范围 : resolution]格式；在过去 1 小时范围内，以 30 秒的步长取样/计算，然后交给 `avg_over_time()` 求平均。
* avg_over_time(.... [1h:30s])：求（当前时间节点-1h ~ 当前时间）时间段的平均内存working Set
* sum by(cluster,pod,container)(...)：同组时间序列相加

以avg_over_time(.... [10m:30s])为例，其中的30秒是子查询的计算步长，真正的平均时间窗口为10m，整体意思为在 10m 这个时间范围内，以 30 秒为 resolution 形成一组时间点，然后 `avg_over_time()` 对这整个时间范围内的值计算平均。

因此，该时间序列每隔10m进行一次取样描点

**container_memory_working_set_bytes**

典型Gauge(瞬时值)；当前容器的 Working Set Memory，单位 bytes。

Working Set Memory：容器当前正在积极使用、较难直接回收的内存。区别container_memory_usage_bytes指标

可回收的 inactive file cache补充：Linux 内存里面可能包含进程匿名内存，活跃 page cache，其他活跃内存

在pass平台中，该指标的标签有（通过裸查询获取）

```

    cluster="bj-caip",
    container="aaa",
    id="/kubepods/...",
    image="...",
    instance="cambricon-train-080",
    job="kubelet",
    metrics_path="/metrics/cadvisor",
    name="...",
    namespace="...",
    node="cambricon-train-080",
    pod="..."
}
```

## 1.2container_cpu_usage_seconds_total

Counter指标；**某个容器从开始运行到当前为止，累计消耗了多少 CPU 时间，单位是秒。**

原始PromQL语句

```
sum by(cluster,pod,container)(
  avg_over_time(
    rate(
      container_cpu_usage_seconds_total{
        cluster=~"%(cluster)s",
        namespace="%(namespace)s",
        container=~"%(container)s",
        pod=~"%(pod)s"
      }[5m]
    )[%(time)s:30s]
  )
)
```

container_cpu_usage_seconds_total{...}[5m]：对当前查询时刻，往前取 5 分钟的原始样本。假设VMNodeScrape的采集间隔为30s，那么“往前取 5 分钟的原始样本”就是采集了10个数据
假设这5m内，共10个数据，此时的10个数据大致为

| 时间 | Counter 值 |
| ---: | ---------: |
|   0s |        100 |
|  30s |        112 |
|  60s |        125 |
|  90s |        137 |
| 120s |        148 |
| 150s |        160 |
| 180s |        172 |
| 210s |        185 |
| 240s |        197 |
| 270s |        208 |

中间数据保留的目的为**判断Counter是否会发生reset**
比如(100，120，140，150，10，30，50)，显然中间出现容器重启

此时rate(...[5m])为 208-100/270 = 0.4，大概表示过去这段时间，该容器平均使用0.4个CPU核
从VMUI的图中来看
![1788509799680](image/硬件指标/1788509799680.png)
其中的数值超过1，有的甚至达到10，这里的含义是，当前时间节点在最近的5m内，平均占用10个CPU核，因为1台服务肯定不是只有一个CPU核的

**示例**

```
avg_over_time(rate(container_cpu_usage_seconds_total...[5m])[30m:30s])
```

在20:20左右，执行一次以上PromQL语句，含义为

1. 从20:20往前推19:50，该时间段内，每30秒计算一次rate(...[5m])，共计算60次
2. 每次计算rate(...[5m])，需要再往前推5m，计算平均占用CPU Core
3. 最后对60次结果进行一个求平均，作为20:20时间点的计算结果

### 2.1 各服务提供的 metrics

#### kubelet 内置 cAdvisor

- `container_memory_working_set_bytes`：容器当前 Working Set 内存，单位为 bytes。
- `container_cpu_usage_seconds_total`：容器累计消耗的 CPU 时间，单位为秒。
- `container_network_transmit_bytes_total`、`container_network_receive_bytes_total`：Pod/容器网络累计发送、接收字节数。
- `container_fs_reads_bytes_total`、`container_fs_writes_bytes_total`：容器文件系统累计读取、写入字节数。

#### kube-state-metrics

- `kube_pod_container_resource_limits`：容器资源 Limit 的声明值，不是实际使用量。

#### Cambricon MLU Exporter

- `mlu_utilization`、`mlu_memory_utilization`、`mlu_power_usage`：MLU 利用率、板上内存利用率和功耗。
- `mlu_mlulink_cntr_read_byte_total`、`mlu_mlulink_cntr_write_byte_total`：MLULink 累计读取、写入字节数。
- `mlu_container`：由 `podresources` collector 提供，用于把 MLU 板卡指标映射到具体容器。

#### NVIDIA DCGM Exporter

- `dcgm_gpu_utilization`、`dcgm_gpu_memory_utilization`、`dcgm_power_usage`：GPU 核心利用率、显存利用率和功耗。

#### Cambricon RDMA Exporter 与 node-exporter

- `rdma_container`：由 RDMA Exporter 提供容器与 RDMA device 的归属关系。
- `node_infiniband_port_data_received_bytes_total`、`node_infiniband_port_data_transmitted_bytes_total`：由 node-exporter 提供 RDMA 端口的实际收发计数。
- RDMA 容器流量 PromQL 会按 `cluster`、`node`、`device` 将上述两类指标关联起来。
