# 指标变化事件词典与组合签名

> 本文回答"指标变化背后发生了什么"。统计口径（每个 metric 是什么、PromQL 怎么算）见 [../大模型指标/metric指标.md](../大模型指标/metric指标.md) 与 [../大模型指标/PromQL分析.md](../大模型指标/PromQL分析.md)；判稳实验设计见 [../稳定推理服务验证.md](../稳定推理服务验证.md)。本文只做一件事：把**曲线变化 → 事件 → 验证路径**变成可查的词典。

## 〇、总纲：一切曲线变化只来自三类事件（外加一类假象）

任何指标异动，归因时只需问是这三类中的哪一类：

| 事件类 | 定义 | 典型触发 |
|---|---|---|
| **E1 负载事件** | 到达速率 / 输入长度 / 输出长度分布发生变化 | 流量突增（用户或压测）、注入超长 prompt、输出变长 |
| **E2 容量事件** | 服务能力相对当前负载不足或劣化 | KV 池满、槽位顶格、卡算力饱和、传输带宽不足、设备降频 |
| **E3 状态事件** | 系统状态迁移 | 冷启动/预热、抢占与驱逐、进程重启（counter 归零）、故障与恢复 |

另有 **X 统计假象**：不是事件，是统计方式造成的表象（见第五节，判读前必须先排除）。

**判读顺序：先排除 X → 区分 E1/E2/E3 → 用联动指标交叉验证。** 单看一条曲线永远无法定论；标准动作是同一时间轴上沿 Queue → Prefill/Decode → KV/Hardware 逐层下钻（见稳定推理服务验证 §22）。

两条地基规则：

1. **avg 平但 p99 尖 = 事件指纹**。`rate(_sum)/rate(_count)` 是观测次数加权平均，一两个离群请求拉不动它；`histogram_quantile` 对尾部敏感。二者背离说明"少数请求经历了特殊事件"而非系统性恶化；avg 与 p99 同步抬升才是系统性事件。
2. **不同 Histogram 的分位数来自不同样本集，不能加减**。"各阶段 P99 之和 ≠ 端到端 P99"；只有 **avg 在同窗口近似可加**（TTFT ≈ queue + prefill 是 avg 级近似，可用此对账）。

## 一、分族词典（↑↓ 的含义 + 联动验证 + PD 双角色注意）

### 1. 请求量 / 成功量（E1 主探测器）

- **到达（http_requests_total）↑ 而完成（request_success_total）不涨** → E2 过载开始：请求进得来、出不去。最早期预警，比延迟指标早。
- **完成曲线掉坑、总 counter 绝对值回落** → E3 进程重启（counter 归零，`increase()` 画假尖/假谷）。先看 `vllm:cache_config_info` 同刻是否换 pod/instance 标签——它是免费的"实例存活探针"。
- **PD 注意**：prefill 的"完成"（KV 交付）早于 decode 的"完成"（整段生成），两条成功曲线天然错位，错位本身不是事件。
- 成功率面板口径 = `finished_reason=~"stop|length"` 占比，即**正常结束原因占比**，不是成功/全部请求之比；流式中断、网关重试不计入。4xx/5xx 另查 http status。

### 2. 并发 running / waiting / 排队率（E1↔E2 转换器）

- **waiting 短尖后回基线**（`0 0 1 0 2 5 3 1 0 0` 型）→ 健康：突发被消化。
- **waiting 单调递增不回落**（`0 3 7 11 18 27 40` 型）→ **Arrival Rate > Service Rate**，判定过载；此时即便没有 5xx 也已超出可持续吞吐。健康判据是 `d(waiting)/dt ≈ 0`，不是 waiting=0。
- **running 顶格不动 + waiting 缓涨** → decode 槽位饱和（顶格值 = MAX_NUM_SEQS）。
- **running/waiting 双降 + 请求量也降** → 流量退潮（E1）；**双降但请求量还在涨** → 危险：上游超时放弃或网关熔断，配合查 4xx/499。
- **PD 注意**：prefill 侧 running 恒 1 是 chunk 预算下的串行形态（非容量事件）；prefill 侧 waiting 尖峰才是 P 实例的过载信号。

### 3. 延迟族（拆解是关键）

**TTFT 上涨二分法**（最重要的两条判读规则）：

| 形态 | 事件 | 下一步 |
|---|---|---|
| TTFT↑ + queue↑ + prefill→ | **E2 排队主导**：过载/突发 | 查请求量、waiting，算 Little's law |
| TTFT↑ + prefill↑ + queue→ | **计算主导**：prefill 本身变慢 | 继续三分（见下） |

**Prefill 计算变慢三分法**：

- prefill↑ + `prefill_kv_computed_tokens`↑ → 真算得多了：超长输入到达（E1，查 prompt 分位/热力图）或 prefix cache 失效（命中率骤降）。
- prefill↑ + kv_computed→ + prompt→ → 同样的活干得慢了：设备效率降（E2/E3，查卡利用率、降频、按 rank 拆单卡）。
- kv_computed↓ + prompt→ → 好事：缓存命中增加，省算力。

**Decode 侧**：

- TPOT/ITL avg↑ + running↑ + waiting↑ → decode 承载不足（E2 判饱和组合）。
- ITL p99 尖而 avg 平 → 偶发事件：抢占后重算间隙（查 preemptions）、调度间隙，非稳态恶化。
- **decode_time↑ 必先问输出长度**：decode_time ≈ 输出长度 × TPOT。`generation_tokens` 同步↑ 是 E1（输出更长）；`generation_tokens` 不变才是生成变慢（E2）。

### 4. Token 族（负载画像）

- 输入 token/min ↑ 而请求数/min → → **平均输入变长**（E1 分布漂移；配合热力图区分整体右移 vs 尾部拉长）。
- 输出 token / 请求数 = 平均输出长度，是 decode_time、decode running 的先行解释变量。
- 每卡每秒归一化用于横向对比；扩容后曲线天然下移（分母变大），不是性能事件。

### 5. KV / 缓存族（E2、E3 主战场）

- **KV usage 随负载涨落、idle 后回落** → 正常容量利用。
- **多轮 idle→load→idle 后基线棘轮式抬升**（10%→20%→35%→50%）→ **泄漏类事件**：KV block 未释放 / 请求未正确结束 / 淘汰异常。最易忽略的慢性病。
- **KV 逼近 100% + preemptions↑ + ITL 尖** → KV 满触发抢占重算（E2→E3 链条；抢占 = 该请求部分 decode 重来，表现为 ITL 长尖）。
- **prefix 命中率口径**：`prefix_cache_hits/queries_total` 单位是 **token** 而非事件次数（vLLM 源码 `in terms of cached tokens`），命中率是 token 级比例。命中数 ≠ 省的算力，省的算力看 `prefill_kv_computed` 的下降。
- 命中率**冷启动低→逐步回升** = cache 预热（E3 正常）；**稳态中骤降** = 缓存被驱逐（KV 压力挤占）或流量 prefix 结构改变（E1）。
- 综合命中率（external+local）分母只有 local query，口径需先确认互斥性，可能重复计数。

### 6. 稳定性族

- preemptions 增量 >0 = 请求因 KV/调度压力被移出运行态；永远与 ITL 尖、KV 水位同轴看。
- NIXL 失败/expired（仅 P 实例上报）→ **PD 专属故障事件**：KV 块在 decoder 读取前过期 = P 算完但 D 太久没来取（通常 D 侧排队拖过有效期）。此指标尖峰时查 **decode 侧 waiting**，不是 prefill 侧。
- spec decode 接受率↓ → 草稿质量退化（模型行为事件），影响有效吞吐而非延迟语义。

## 二、组合签名速查表

| # | 签名（同时间轴同时出现） | 背后事件 | 类型 | 决定性佐证 |
|---|---|---|---|---|
| S1 | waiting↑ + queue p99↑ + TTFT avg↑ + prefill→ | 突发流量过载排队 | E1→E2 | 请求量同刻尖峰；完成率未跌 = 尚未熔断 |
| S2 | TTFT p99尖 + avg平 + prompt p99尖 | 个别超长请求 | E1 | prompt 热力图尾部亮行 |
| S3 | prefill avg↑ + kv_computed avg↑ | 输入整体变长 | E1 | 输入 token/min ↑、请求数不变 |
| S4 | prefill avg↑ + kv_computed平 + prompt平 | 设备效率劣化 | E2/E3 | 卡利用率/降频/单卡异常（按 rank 拆） |
| S5 | 命中率↓ + kv_computed↑ + TTFT↑ | 缓存失效或被驱逐 | E3/E2 | KV 水位、驱逐指标 |
| S6 | running 顶格 + waiting缓涨 + TPOT↑ | decode 槽位饱和 | E2 | running 顶格值 == MAX_NUM_SEQS |
| S7 | decode_time↑ + generation_tokens↑ + TPOT平 | 输出更长 | E1 | 输出 token/请求 ↑；**不是故障** |
| S8 | KV→100% + preemptions↑ + ITL p99尖 | KV 池满→抢占重算 | E2→E3 | 三指标同刻联动 |
| S9 | idle 后 KV 基线逐轮抬升 | KV/请求泄漏 | E3 | 多轮 load-idle 实验复现 |
| S10 | 完成量掉坑 + counter 绝对值回落 + cache_config_info 换 pod | 进程重启 | E3 | 非性能事件，先剔除再分析 |
| S11 | NIXL expired↑ + decode waiting↑ | D 拖延取 KV 过期（PD 特有） | E2 | 查 D 侧而非 P 侧 |
| S12 | 请求量↑ + 完成量↓ + 4xx/504↑ + queue↑↑ | 过载引爆超时熔断 | E2 终局 | 错误码与 queue 同刻 |
| S13 | 过载后降载，各项回原基线 | 可恢复（健康） | — | Recovery 判据 |
| S14 | 过载后降载，waiting/TTFT 不回落 | 不可恢复（病态） | E3 | 死锁/泄漏/连接堆积 |

## 三、判稳元规则（避免单点误判）

1. **看趋势不看单点**：`slope(waiting)≈0`；30min 切 6×5min 窗口看 TTFT p99 是否单调恶化（工程阈值：last/first < 1.2）。一次尖峰不算不稳定，持续棘轮才算。
2. **目标是 Maximum Sustainable Throughput 而非 Maximum QPS**：可持续 = Arrival≈Completion + 各项无趋势性增长 + 短时过载可恢复（S13 而非 S14）。
3. **客户端 + 服务端两侧互证**：面板指标都是服务端的（不含网关/网络）。客户端 TTFT 恶化而服务端无异常 → 问题在服务边界之外（链路事件，E1/E2/E3 之外的第四类）。

## 四、PD 架构专项提醒

一个请求的生命周期被劈成两半，每个延迟指标两侧语义不同：

```
到达 → [P:排队] → [P:prefill计算] → [KV经NIXL/RDMA传输] → [D:排队] → [D:逐token生成] → 完成
       └──────── prefill侧指标只覆盖这段 ────────┘           └── decode侧指标只覆盖这段 ──┘
```

- decode 侧 Prefill 延迟 ≈ 0（KV 传来的）、prefill 侧 Decode/ITL/TPOT 恒 0 或无数据——**正常，不是故障**。
- 单看任一侧 E2E 都低估（两侧互补，相加近似）。
- 用户真实 TTFT ≈ prefill TTFT + KV 传输 + decode TTFT；真实 E2E ≈ 两侧 E2E 之和 + 传输。
- prefill/decode 成功曲线天然错位（prefill 先完成）。
- 所有指标按 `label_role_name` 分拆看，不做聚合。

## 五、统计假象清单（判读前先排除）

| 假象 | 成因 | 排除方法 |
|---|---|---|
| 曲线掉坑/假尖 | 进程重启 counter 归零 | 对照 `cache_config_info` 存活与 counter 绝对值 |
| avg 曲线断点 | `rate(_count)=0` 无新观测 | 正常空窗，非故障 |
| p99 数值贴桶边界或越界跳变 | 直方图桶粗，外推插值 | 看热力图原始桶，别迷信分位数值 |
| 曲线随 step 变形 | `[time:30s]` 子查询平滑（5m 平滑可把 running=1 抹成 0.07） | 换细 step 复核 |
| E2E 单侧偏低 | PD 把生命周期劈两半 | 两角色相加近似 |
| "命中次数"虚高 | hits/queries 实为 token 口径 | 用 kv_computed 交叉验证真实省算力 |
| 不同服务/角色聚合后语义混淆 | 聚合掉了 label_role_name | 始终 by(namespace, label_role_name) 分拆 |
