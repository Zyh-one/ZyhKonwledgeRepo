# 指标关联：`http_requests_total` ↔ `vllm:request_success_total`

> 本文回答一个问题：**HTTP 层账本与引擎终态账本之间是什么关系？能否互相换算？**（另附 §5：抢占与 KV 利用率的关联。）
> 结论先行：**没有严格的数值映射**。两者记录的是不同集合——`http` 记录"HTTP 生命周期完结"的请求（按 `status` 分桶），`success` 记录"在引擎内走到终态"的请求（按 `finished_reason` 分桶）。交集很大但互不包含，只能做**成分分解式对账**，不能做恒等换算。两指标的单独口径见 [PromQL.md](./PromQL.md) 1.1/1.2。

## 1. 映射总表：status → 是否被 success 捕捉、落哪个桶

```
http_requests_total（全量，按 status 记账）
  ├─ 4xx  → 100% 不进 success（校验拒绝，请求根本没进引擎）
  ├─ 5xx  → 拆两种：
  │     ① 引擎终态错误：finished_reason=error → 恒转 HTTP 500   → 进（error 桶，两边同时计）
  │     ② 入口/准入拒绝：过载 503、提交引擎前的异常 500        → 不进（无终态可记）
  └─ 2xx  → 大部分最终会进，但有缺口：
        · 在途请求（正在生成中）：暂未进，等引擎终态后补上（时序缺口）
        · 崩溃/重启时死在半路的：永不进（HTTP 已记完 2xx，引擎再无终态）——永久缺口
        · 落桶不定：stop / length / abort / error / repetition 五个桶都可能
```

反向看（success → http）同样不严格：

- `abort`（流式中断）的请求在 http 侧**早已按 2xx 计完**（SSE 首个响应头发出时刻 status 即定格，中途断开不改写）；
- `error` 的请求两边同时计数（http 侧 5xx、success 侧 error 桶）——是唯一"双计"的成分。

**判断标准只有一条：请求是否在引擎内走到了终态（获得某个 `finished_reason`）。与 HTTP status 没有必然绑定。**

## 2. 由此派生的三个差值口径（各有用途）

| 差值               | 公式                                  | 含义                                     | 主用途                 |
| ------------------ | ------------------------------------- | ---------------------------------------- | ---------------------- |
| **D 总差值** | `http到达 − success(5reason总和)`  | 进不来（被拒）+ 还没出来（在途）         | 过载早期预警（见 §3） |
| **弃单指纹** | `http(2xx) − success(stop+length)` | 在途 + 流式中断(abort) + 引擎错误(error) | 流式弃单排查           |
| **纯净在途** | 上面两者都剔除 abort/error 后的残差   | 校验/提交前缓冲 + 流式收尾 + PD 移交阶段 | 口径边界分析           |

恒等关系（abort=error=0 时成立，可作对账校验）：

```
D = 4xx + 5xx + [2xx − (stop+length)]
```

## 3. D 的分解与实测对账

对任意窗口（counter 数学恒等式，已确认）：

```
D = 入口拒绝项 + Δ在途库存 + 观测残差
    │              │             └─ HTTP 层在途中引擎 gauge 看不见的部分
    │              │                （校验/提交前缓冲、流式收尾、PD 的 KV 移交阶段）
    │              └─ 引擎侧 = Δ(running + waiting)，可用 gauge 测
    └─ 4xx（校验拒绝：超长/参数错，E1）+ 5xx（过载/准入拒绝，E2）
```

**实测一（deepseek-v4-dp2tp4，standalone，近 1h 窗口，2026-09-29 查询）：**

| 项                 | 值                   | 说明                                                                                            |
| ------------------ | -------------------- | ----------------------------------------------------------------------------------------------- |
| A http 到达        | 1433                 | 2xx=1400，4xx=0，**5xx=33**                                                               |
| B 引擎完成         | 1345                 | stop=1341，length=4，abort/error/repetition 全 0                                                |
| D = A − B         | 88                   | 分解 = 33(拒绝) + 55(在途净增，其中引擎侧 Δ=40) ✓ 精确闭合                                    |
| **关键证据** | 5xx=33 而 error 桶=0 | 这 33 个请求**根本没进引擎**（入口/准入拒绝），且该服务 running=69 高位——过载信号（E2） |

**实测二（glm52-8-pd decode 角色，PD 对照）：**

| 项            | 值               | 说明                                                                                                                                                                                        |
| ------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A / B / D     | 2111 / 2071 / 40 | 4xx=5xx=0，abort=error=0                                                                                                                                                                    |
| 引擎侧 Δ在途 | −1              | running/waiting 全程平稳（12+1）                                                                                                                                                            |
| 残差          | 40               | λ=0.59/s × 隐含驻留 ~67s ≈ 40 → 指向**PD decode 的 KV 等待移交阶段不计入 running/waiting 口径**（合理推断，尚待确认）。decode 的真实在途 = D 差值 + 引擎 gauge，单看 gauge 会低估 |

## 4. 判读词典（D 的形态 → 事件）

| D 形态                                   | 事件                                             | 下一步                                |
| ---------------------------------------- | ------------------------------------------------ | ------------------------------------- |
| 稳定小正值，4xx 在涨                     | E1 超长/非法参数被校验拒绝                       | 查 prompt 长度分布                    |
| 稳定小正值，5xx 在涨且 error 桶=0        | **E2 过载/准入拒绝（最有价值的早期预警）** | 查 waiting、KV 水位                   |
| 瞬时尖峰后回落，waiting/running 同刻上升 | 长生成服务的正常滞后（λ×E2E 效应），非故障     | Little 定律估算预期在途               |
| 持续偏大、4xx/5xx 全零、引擎 gauge 平    | HTTP 层/引擎外滞留（PD 移交、提交前缓冲）        | 分角色拆，查 NIXL 状态                |
| **负值**                           | 统计假象：counter 归零（进程重启）               | 对照`cache_config_info` 换 pod 时刻 |

## 5. 抢占 ↔ KV 利用率关联（`vllm:num_preemptions_total` ↔ `vllm:kv_cache_usage_perc`）

> 两指标单独语义见 [PromQL.md](./PromQL.md) 1.5。以下结论来自 glm52-8-pd decode 实测（2026-09-29，engine 粒度 30s/60s 复核，北京时间）。

**正确结论是三段式因果链，而不是"抢占时 KV 突然增高"（该说法时间顺序颠倒）：**

```
KV 冲高位/瞬时打满（前置，必要不充分）
  → 某 step 分配 block 失败、preemptions 跳变（事件，唯一决定性信号）
  → KV 回落 + running 阶梯下掉 + ITL 尾巴（事后指纹）
```

实测相位表（engine4，17:51 事件）：

| 相位       | 北京时间          | KV            | preemptions |
| ---------- | ----------------- | ------------- | ----------- |
| 前置       | 17:49 ~ 17:50:30  | 0.57 → 0.946  | 3（不动）   |
| 事件       | 17:51:00 ~ 17:51:30 | 0.83 → 0.78 | **3 → 12**  |
| 后果       | 17:52 ~ 17:53     | 0.83 → 0.128  | 12（不动）  |

**两个口径陷阱：**

1. 抢占发生时刻 KV 是**回落**的（被踢请求释放 block）；"增高"发生在事件**之前**。
2. 触发条件是**瞬时打满**（引擎内部那一刻 100%），但 30s 采样的 gauge 观测值可能只有 0.8~0.95——观测不到 100% 不代表没打满。

**判读分工：** KV 高位 = 警惕区（状态），counter 跳变 = 事件确认（账本）。不能用"KV 增高"当抢占探测器——engine4 全下午 44 个采样点 >0.9、仅 12 次抢占（误报方向）；两个已验证事件观测峰值仅 0.946/0.905（漏检方向）。

**事件归属引擎的方法：** 两 metric 均带 `engine` 内部标签（engine 序号跨 pod 全局唯一，每 (pod, engine) 一条序列），按 `sum by(engine)(vllm:num_preemptions_total{...})` 差分——哪条序列在跳，事件就在哪个引擎，归属判定与 KV 无关。

**结论等级：** 三段式因果链与相位表、engine 归属方法——已确认（3 个事件实测）；"内部打满时刻必然 100%、观测值可能不足"——合理推断（源码语义 + 观测组合，未看引擎内部分配日志）。
