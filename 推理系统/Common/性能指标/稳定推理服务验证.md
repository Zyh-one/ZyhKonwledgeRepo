# 稳定大模型推理服务测试与判定方法

## 1. 文档目标

本文用于回答一个核心问题：

> 一个稳定、健康、可上线的大模型推理服务，应该如何通过可执行的测试和指标进行判断？

重点不是停留在“TTFT 要稳定”“队列不能太长”这类概念描述，而是把每个判断项落实为：

- 如何设计测试请求
- 使用什么压测方式
- 从客户端还是服务端采集数据
- 具体监控哪些指标
- 如何定义“稳定”
- 如何定位不稳定的原因

本文适用于基于 vLLM 等推理框架部署的常规大模型在线推理服务。

---

## 2. 测试体系基本原则

推理服务测试需要同时从两侧观察：

```text
客户端压测工具evalscope  --> 判断用户实际体验

服务端推理框架 / Exporter / Gateway Metrics --> 解释为什么性能发生变化
```

两类数据不能互相替代。

因此始终采用：**客户端指标 + 服务端内部指标**联合判断，具体系统解释性

---

## 5. 第二层：Request Queue 稳定性

Queue 是判断推理服务是否过载的一级核心指标。

### 5.1 vLLM 指标

重点监控：

```text
vllm:num_requests_running
vllm:num_requests_waiting
```

如果当前版本支持，还可以监控：

```text
vllm:num_requests_waiting_by_reason
```

### 5.3 健康状态

例如：

```text
Waiting: 0 0 1 0 2 5 3 1 0 0
```

说明系统出现短时 Burst 后能够自行消化：

```text
短暂积压
    ↓
系统消费
    ↓
重新回到基线
```

### 5.4 不健康状态

例如：

```text
0
3
7
11
18
27
40
...
```

意味着：

```text
Arrival Rate > Service Rate
```

即使尚未出现 503 / 504，也已经可以判定当前负载超过服务的可持续处理能力。

### 5.5 推荐量化规则

不要要求 Waiting Requests 永远等于 0。

更合理的判断方式：

```text
30min 稳态窗口：

Waiting P50 接近基线
Waiting P99 在可接受范围

并且：

slope(waiting_requests) ≈ 0
```

核心条件：

```text
d(Waiting Requests) / dt ≈ 0
```

即没有持续正增长趋势。

## 6. 第三层：TTFT 稳定性

TTFT 反映用户从发送请求到收到第一个 Token 的等待时间。

必须同时从客户端和服务端观察。

### 6.1 客户端 TTFT

EvalScope 统计：

```text
TTFT Avg
TTFT P50
TTFT P90
TTFT P99
```

客户端 TTFT 最接近真实用户体验，因此应作为最终 SLA 判断的主要依据。

### 6.2 服务端 TTFT

vLLM 可监控：

```text
vllm:time_to_first_token_seconds
```

PromQL 示例：

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(vllm:time_to_first_token_seconds_bucket[5m])
  )
)
```

### 6.3 TTFT 拆解

还应同时监控：

```text
vllm:request_queue_time_seconds
vllm:request_prefill_time_seconds
```

可近似理解为：

```text
TTFT
≈ Queue Time
+ Prefill Processing
+ 其他框架开销
```

### 6.4 Queue 导致 TTFT 上涨

如果：

```text
TTFT P99       ↑↑
Queue Time P99 ↑↑
Prefill Time   →
```

说明 TTFT 恶化主要来自请求排队。

### 6.5 Prefill 导致 TTFT 上涨

如果：

```text
TTFT P99       ↑↑
Queue Time     →
Prefill Time   ↑↑
```

说明 Prefill 本身执行时间正在恶化。

需要检查：

```text
Input Length
Batch Size
GPU/MLU Utilization
Prefix Cache
Attention 计算
通信开销
```

---

## 7. 如何量化 TTFT 稳定

不要只使用：

```text
TTFT < 5s
```

作为唯一标准。

应该同时包含绝对 SLA 和时间稳定性。

### 7.1 绝对 SLA

例如：

```text
TTFT P99 < 5s
```

具体阈值由业务决定。

### 7.2 时间稳定性

将 30 分钟测试划分为：

```text
6 × 5min Window
```

分别计算 TTFT P99。

健康：

```text
3.8
4.0
3.9
4.1
3.8
4.0 s
```

不健康：

```text
3.5
4.1
5.3
7.2
10.5
15.8 s
```

即使整体 Avg TTFT 还可以，只要持续恶化，也应判定当前 workload 下服务不稳定。

### 7.3 第一版工程规则

可以先定义：

```text
Last 5min TTFT P99
-------------------- < 1.2
First 5min TTFT P99
```

即最后窗口相对第一个稳定窗口的 P99 增幅不超过 20%。

20% 只是初始工程阈值，应根据实际 SLA 调整。

---

## 8. 第四层：Prefill 能力稳定性

### 8.1 测试方法

尽量降低 Decode 对实验的影响：

```text
Output = 16 / 32 Tokens
```

分别测试：

```text
Input:
1K
4K
8K
16K
32K
```

对每个 Input Length，再逐级增加请求速率：

```text
1 RPS
2 RPS
4 RPS
6 RPS
8 RPS
...
```

每档持续 10~30 分钟。

### 8.2 服务端指标

重点观察：

```text
vllm:num_requests_running
vllm:num_requests_waiting
vllm:request_queue_time_seconds
vllm:request_prefill_time_seconds
vllm:request_prompt_tokens
vllm:request_prefill_kv_computed_tokens
```

客户端同时观察：

```text
TTFT P50/P90/P99
Input Tokens/s
Success Rate
```

### 8.3 Prefill 饱和判断

如果随着 Rate 增加：

```text
Input Tokens/s 基本不再增加
```

同时：

```text
Waiting Requests ↑
Queue Time ↑
TTFT ↑
```

说明 Prefill 已达到 Saturation Point。

---

## 9. 第五层：Decode 能力稳定性

### 9.1 测试方法

尽量降低 Prefill 影响：

```text
Input  = 128 / 256 Tokens
Output = 1024 / 2048 Tokens
```

再逐级提高 Rate 或 Parallel。

### 9.2 客户端指标

重点统计：

```text
TPOT Avg
TPOT P50
TPOT P90
TPOT P99

ITL P50
ITL P90
ITL P99

Output Tokens/s
Request Throughput
```

TPOT 表示除首 Token 外平均每生成一个 Token 所需时间。

ITL 表示连续 Token 之间的实际时间间隔。

### 9.3 vLLM 服务端指标

重点观察：

```text
vllm:inter_token_latency_seconds
vllm:request_time_per_output_token_seconds
vllm:request_decode_time_seconds
vllm:request_generation_tokens
vllm:num_requests_running
vllm:num_requests_waiting
```

---

## 10. 如何判断 TPOT 稳定

例如：

```text
Input    = 256
Output   = 2048
Rate     = 5 RPS
Duration = 30 min
```

每 5 分钟统计一次 TPOT P99。

健康：

```text
52ms
54ms
55ms
53ms
56ms
55ms
```

不健康：

```text
50ms
65ms
90ms
130ms
180ms
250ms
```

如果同时：

```text
num_requests_running ↑
num_requests_waiting ↑
```

则说明 Decode 承载能力已经不足。

---

## 11. 第六层：KV Cache 健康性

重点监控：

```text
vllm:kv_cache_usage_perc
```

### 11.1 测试方法

设计：

```text
阶段 A：Idle 5 min
阶段 B：Load 20 min
阶段 C：Idle 10 min
```

即：

```text
0 RPS
 ↓
固定 RPS
 ↓
0 RPS
```

### 11.2 同时观察

```text
vllm:kv_cache_usage_perc
vllm:num_requests_running
vllm:num_requests_waiting
```

### 11.3 健康情况

例如：

```text
Idle:
KV = 10%

Load:
KV → 65%

Load结束:
KV → 回落或进入稳定 Cache 状态
```

重点不是要求 KV Usage 等于 0，而是判断：

> Active Request 已恢复正常后，KV Cache 是否存在无界增长。

### 11.4 异常情况

如果多轮：

```text
Idle → Load → Idle
```

后 KV baseline 持续抬升：

```text
10%
20%
35%
50%
65%
...
```

且无法由 Cache 行为解释，就需要考虑：

```text
KV Block 未释放
Request 未正确结束
Cache 淘汰异常
KV Cache 泄漏
```

## 12. 第七层：Prefix Cache 稳定性

如果开启 Prefix Cache，可重点监控：

```text
vllm:prefix_cache_queries
vllm:prefix_cache_hits
```

命中率可以通过：

```promql
rate(vllm:prefix_cache_hits[5m])
/
rate(vllm:prefix_cache_queries[5m])
```

计算。

### 12.1 Cold Prefix Test

构造完全不同 Prompt：

```text
Request A
Request B
Request C
Request D
...
```

期望 Prefix Cache Hit Rate 很低。

### 12.2 Hot Prefix Test

所有请求共享：

```text
固定 System Prompt
+
固定长公共 Prefix
+
不同尾部问题
```

期望：

```text
Prefix Cache Hit Rate ↑
```

同时观察：

```text
vllm:request_prefill_kv_computed_tokens
TTFT
```

如果 Hit Rate 明显增加，但 TTFT 完全不变，需要继续分析 Prefill 是否本来就不是瓶颈，或者 Queue 等其他部分是否占主要时间。

---

## 13. 第八层：硬件资源稳定性

推理框架指标之外，还需要结合 GPU / MLU Exporter。

至少监控：

```text
Device Utilization
Memory Used
Memory Total
Temperature
Power
```

具体指标名取决于集群中的 Exporter，应从真实 `/metrics` 中确认：

```bash
curl <exporter>/metrics | grep -Ei 'util|memory|temperature|power'
```

### 13.1 测试方法

采用：

```text
Idle
 ↓
Load 30 min
 ↓
Idle
```

### 13.2 判断内容

观察：

```text
Memory 是否进入稳定状态
Utilization 是否随负载变化
请求结束后 Utilization 是否正常下降
是否存在单张设备异常
Temperature / Power 是否持续异常
```

不要只看平均设备利用率。

并行推理场景应尽量按照：

```text
Node
Pod
Rank
Device
```

分别观察资源。

---

## 14. 第九层：错误率稳定性

客户端统计：

```text
Successful Requests
Failed Requests
Success Rate
HTTP Status
Timeout
```

Gateway / Ingress 建议拆分：

```text
2xx
4xx
5xx
503
504
```

不要只看总成功率。

错误状态必须和：

```text
Queue
TTFT
TPOT
Resource
```

按同一时间轴关联分析。

---

## 15. 第十层：Recovery 恢复能力

稳定服务不仅要求正常状态下不出问题，还必须验证：

> 从短时过载中能否自行恢复。

### 15.1 测试方法

设计：

```text
0 ~ 10min：
5 RPS

10 ~ 15min：
15 RPS

15 ~ 30min：
5 RPS
```

即：

```text
Normal
  ↓
Overload
  ↓
Normal
```

### 15.2 监控指标

客户端：

```text
TTFT
TPOT
ITL
Error Rate
Request Throughput
```

服务端：

```text
vllm:num_requests_waiting
vllm:num_requests_running
vllm:kv_cache_usage_perc
vllm:request_queue_time_seconds
```

### 15.3 健康恢复

过载期间：

```text
Queue ↑
TTFT ↑
```

降低回正常 Rate 后：

```text
Queue ↓
    ↓
TTFT ↓
    ↓
TPOT ↓
    ↓
重新回到原稳态
```

### 15.4 不健康恢复

如果降低回正常 Rate 后依然：

```text
Waiting 长时间不下降
TTFT 持续高位
TPOT 持续异常
错误率没有恢复
```

则说明服务经历一次过载后无法恢复正常状态。

---

## 16. 稳态测试的时间窗口设计

判断稳定性不能只比较一次平均值。

建议：

```text
总测试时间 = 30 min
Window      = 5 min
```

得到 6 个窗口。

对每个 Window 计算：

```text
TTFT P50/P99
TPOT P50/P99
ITL P99
Waiting P50/P99
Request Throughput
Error Rate
Input Tokens/s
Output Tokens/s
```

然后重点判断是否存在持续趋势，而不是只看 30 分钟整体平均值。

---

## 17. Maximum Sustainable Throughput

生产环境真正应该寻找的不是 Maximum QPS，而是：

> Maximum Sustainable QPS / Maximum Sustainable Throughput

即：

> 在持续运行过程中不会造成 Queue、Latency、Error 和 Resource 持续恶化的最大请求速率。

一个负载档位可以认为“可持续”，至少应满足：

```text
Request Completion Rate ≈ Arrival Rate
Waiting Requests 无持续增长
TTFT 无持续增长
TPOT / ITL 无持续增长
Error Rate 保持稳定低位
KV / Memory 无无界增长
```

并能够持续 30min、1h，甚至更长时间。

## 20. 最终稳定性测试矩阵

| 层级         | 测试方法                  | 客户端指标                       | 服务端指标                            | 核心判稳条件           |
| ------------ | ------------------------- | -------------------------------- | ------------------------------------- | ---------------------- |
| 请求入口     | 固定 Rate 30min           | Request Throughput、Success Rate | Gateway RPS                           | Arrival ≈ Completion  |
| Scheduler    | 固定 Rate                 | TTFT                             | `vllm:num_requests_waiting`         | Queue 无持续增长       |
| TTFT         | 固定 Input/Output         | TTFT P50/P99                     | `vllm:time_to_first_token_seconds`  | 分窗口无持续恶化       |
| Queue        | 阶梯 Rate                 | TTFT                             | `vllm:request_queue_time_seconds`   | P99 无趋势性增长       |
| Prefill      | Long Input / Short Output | TTFT、Input TPS                  | `vllm:request_prefill_time_seconds` | 吞吐稳定、Queue 不累积 |
| Decode       | Short Input / Long Output | TPOT、ITL、Output TPS            | `vllm:request_decode_time_seconds`  | TPOT/ITL 无持续恶化    |
| KV Cache     | Load → Idle              | -                                | `vllm:kv_cache_usage_perc`          | 无无界增长             |
| Prefix Cache | Cold / Hot Prefix         | TTFT                             | `prefix_cache_hits/queries`         | 命中行为符合预期       |
| Hardware     | Load → Idle              | -                                | GPU/MLU Util、Memory                  | 和负载同步，无单卡异常 |
| Error        | 固定/高负载               | Success、HTTP Status             | Gateway 5xx/503/504                   | 错误率稳定低位         |
| Recovery     | Normal→Overload→Normal  | TTFT/TPOT/Error                  | Waiting/KV/Queue                      | 能恢复原稳态           |
| Long Run     | 1h/6h/24h                 | 全部                             | 全部                                  | 无趋势性退化           |

## 21. 健康推理服务的最终判定标准

一个推理服务可以认为已经进入稳定运行状态，需要同时满足：

### Traffic

```text
Arrival Rate ≈ Completion Rate
```

### Queue

```text
Waiting Requests 可以短暂波动
但不能持续增长
```

### TTFT

```text
满足 SLA
+
不同时间窗口之间没有持续恶化
```

### TPOT / ITL

```text
满足 SLA
+
Decode 持续生成速度保持稳定
```

### KV Cache

```text
随负载变化
+
能够进入新的稳定状态
+
不存在无界增长
```

### Hardware

```text
利用率与流量相关
+
Memory 稳定
+
设备之间无异常不均衡
```

### Error

```text
错误率处于可接受低位
+
不会随运行时间持续增加
```

### Recovery

```text
短时过载后
能够自动重新进入原有稳态
```

## 23. 总结

稳定推理服务测试不应停留在：

```text
TTFT 要低
TPOT 要低
GPU 利用率要高
```

而应该建立：

```text
Workload
    ↓
Client Metrics
    ↓
Server Metrics
    ↓
Time Window
    ↓
Trend Analysis
    ↓
Stable / Unstable
```

真正需要回答的是：

```text
在固定 workload 下：

请求是否可以持续被系统消费？

Queue 是否会无限增长？

TTFT 是否随时间恶化？

TPOT / ITL 是否随时间恶化？

KV Cache 是否可以保持动态平衡？

硬件资源是否保持稳定？

短时过载后服务是否能够恢复？

最大可以稳定承载多少负载？
```

最终目标不是获得一个：

```text
Maximum QPS
```

而是得到：

```text
Maximum Sustainable Throughput
```

并明确对应的：

```text
TTFT
TPOT
ITL
Queue
KV Cache
Hardware
Error Rate
```
