# 多模型稳定部署

## 1.单卡部署

- 单卡稳定部署的死地：OOM（显存溢出，Out of Memory）
- 核心原则：**隔离**，绝不能让模型“自由发挥”吃显存。
	- 框架层的隔离（基础）：vllm和sglang启动时强制限制启动参数（--gpu-memory-utilization）
		- **待验证**
	- 进程层的隔离：该部分主要由nvidia原生支持的相关技术，比如MPS限制等，
		- 部分验证
	- 调度层（K8s）的隔离：该部分主要依托k8s，及其相关原生插件
- 可参考资源：
	- NVIDIA  Triton Inference Server
- 下面结合上述内容，设计”单卡混合部署“的具体方案和验证流程

### 1.1验证流程

**实验一：纯框架层**
1. 目标：学会手动控制显存分配。
2. 动作： 找一台 GPU 服务器。打开两个终端，尝试同时启动两个 vLLM 或 SGLang 服务（跑比较小的模型，比如 Qwen-1.5B）。
3. 关键点： 第一台启动时加上参数 `--gpu-memory-utilization 0.4` 和 `--port 8000`；第二台加上 `--gpu-memory-utilization 0.4` 和 `--port 8001`。
4. 观察： 看看 `nvidia-smi` 中显存是否被乖乖分成了两块？然后同时给两个端口发请求，看会不会报错。

**实验二：使用 Triton 管理多个模型** 

1. 目标： 体验工业级推理服务器如何管理多模型。
2. 动作： 安装 Triton 的 Docker 镜像。按照官方教程，在本地创建一个 `model_repository`（模型仓库）文件夹，里面放两个不同的小模型（比如一个 ONNX 格式的图像分类模型，一个 Python 脚本模型）。
3. 观察： 启动 Triton Server，观察它是如何在一个进程内，稳定地把这两个模型加载进显存并同时提供 HTTP API 服务的。
    

**实验三：压榨算力**
1. 目标： 验证算力切分带来的性能提升。
2. 动作： 在宿主机上启动 `nvidia-cuda-mps-control` 后台进程。然后重复实验一（启动两个模型进程）。
3. 观察： 使用发压工具（如 Apache Bench 或 JMeter）同时给两个模型打并发。对比“开启 MPS”和“不开启 MPS”时，GPU 的 `Volatile GPU-Util`（算力利用率）和吞吐量的差异。

- 如何理解sglang模型实例的“稳定运行”？
	- **启动稳定**
		- 模型正常加载，单请求正常返回
		- 具体方法
			- /health 正常响应
	- **功能稳定**
		- 完成一次真实请求
		- 具体方法
			- 分别发送“非流式”和“流式”请求，查看请求是否成功
			- （请求的具体内容和特征，后续设计）
	- **资源稳定
		- 在没有高负载时，实例稳定使用GPU
		- 具体方法：
			- 启动初期，3~5分钟持续记录GPU资源
				- 观察显存占用和GPU Utility是否稳定，日志中是否出现error等
			- 发送warmup请求，持续记录1~2分钟的GPU资源
				- 观察是否OOM，GPU util 在请求结束后是否回落，上升后的显存是否持续稳定
