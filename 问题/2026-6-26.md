## 2.要点

1. 编写算法本质上是在回答两个问题：
   1. 问题：
      1. 当前这一轮kernel需要调用多少个thread？
      2. 每个thread需要计算哪些内容？
   2. 大致设计思路：
      1. 确定总任务量：
      2. 确定thread / block数量如何覆盖任务空间
      3. 确定thread idx到数据位置的映射规则
      4. 确定每个thread的具体计算逻辑
2. CudaSteam：
   1. Cuda执行队列；由CUDA runtime管理；管理调度具体kernel的执行顺序，比如 linear_kernel等
   2. 核心背景：（进程）
      1. 某个**进程**在某张 GPU 上使用 CUDA 时，会有一个 CUDA context；
      2. 这个 context 里面可以创建多个 stream；这些 stream 用于向这张 GPU 提交任务。
      3. 故不难推断，Stream的创建由CPU端的代码所指定的
   3. 整体链路：
      1. 其实cudaStream就是一个管理kernel任务执行顺序的逻辑队列；同一个stream内按顺序执行，不同stream之间可能并发执行
      2. cudaStream调度出的kernel任务还会被GPU Scheduler按照Grid，Block，Thread的层次进行划分
   4. 每个kernel的执行都会经历Cuda Stream的调度和选择，但是kernel内部是没有指定stream的相关参数，
3. shredMem：作为cuda算子执行中的一个参数，控制共享GPU显存空间的大小
   1. 本质：一个 block 内所有 thread 共同使用的一块高速临时缓存；**这里可扩展GPU存储体系**
   2. **按block分配**；同一block中的所有thread共享该shared memory的数据
   3. 在具体使用过程中，shared memory经常用来做thread之间的数据交换
   4. 由于多个thread共享同一块数据，因此需要做同步（__syncthreads）
      1. 表示：等待当前 block 内所有 thread 都完成 shared memory 写入后，再继续执行后面的代码。
4. KernelLab本质上还处于在pytorch上层做的一些自定义算子的操作，其中大量引用了pytorch的相关语句，比如cpu侧创建tensor张量；所以，后续可以考虑如何完全剥离pytorch，可能会涉及实现runtime等层次的内容；
