# Predictor Monitor 组件协作与数据流

## 1. 页面定位

Predictor Monitor 是一个由多个组件共同组成的监控仪表盘。

页面不是由一个组件独立完成全部工作，而是按职责分为业务入口、监控外壳、条件筛选和图表展示四个层次。各层通过 Angular 组件输入、输出事件和状态变化相互配合。

整体目标是：

> 将 Predictor 的业务信息转换为统一的监控上下文，再根据用户选择的时间、版本和资源条件，驱动不同类型的监控图表。

## 2. 组件层次

```text
PredictorMonitorComponent
业务入口：读取 Predictor，准备监控初始参数
        │
        ▼
ContainerMonitorComponent
监控外壳：管理监控类型、时间、步长和当前筛选结果
        │
        ├── MetricVariableSelectComponent
        │   筛选器：管理版本、Pod、容器或请求路径等条件
        │
        └── 具体监控组件
            ├── ContainerHardwareMonitorComponent
            ├── ContainerServiceMonitorComponent
            └── LlmserviceMonitorGraphComponent
                图表层：根据当前监控上下文查询并展示数据
```

这个结构的核心特点是：上层决定“监控什么”，下层负责“怎样展示监控结果”。

## 3. 各层组件职责

| 层次       | 组件                              | 宏观职责                                                      |
| ---------- | --------------------------------- | ------------------------------------------------------------- |
| 业务入口层 | `PredictorMonitorComponent`     | 获取 Predictor 数据，准备时间范围、版本、资源标识和筛选项定义 |
| 页面协调层 | `ContainerMonitorComponent`     | 维护页面公共状态，组织筛选器和不同监控类型的子组件            |
| 筛选表单层 | `MetricVariableSelectComponent` | 展示动态筛选项，处理条件之间的关联，输出完整的筛选结果        |
| 监控展示层 | Hardware / Service / LLM 组件     | 接收时间和筛选上下文，加载对应监控数据并渲染图表              |

## 4. 初始化时的数据传递顺序

页面首次进入时，数据主要按“从上到下”的方向传递。

```text
Predictor 业务数据
        │
        ▼
业务入口组件整理监控初始参数
        │
        ▼
监控外壳接收页面级参数
        │
        ├── 将筛选项定义交给筛选组件
        │
        └── 将时间、布局和资源信息交给监控展示组件
        ▼
筛选组件建立默认选择状态
        │
        ▼
完整监控上下文形成
        │
        ▼
当前监控类型开始展示数据
```

在这个阶段，`PredictorMonitorComponent` 提供的不是具体图表数据，而是构建监控页面所需的业务上下文。

## 5. 用户操作时的组件协作

用户更改版本、Pod、容器或请求路径时，数据会先“向上回传”，然后再“向下传播”。

```text
用户修改筛选条件
        │
        ▼
筛选组件更新内部表单状态
        │
        ▼
筛选组件向上输出完整筛选结果
        │
        ▼
监控外壳更新当前监控上下文
        │
        ▼
新的上下文向下传递给当前图表组件
        │
        ▼
图表组件停止旧的数据加载周期
        │
        ▼
按新的筛选条件加载并展示数据
```

这个过程体现了组件之间的双向协作，但不是直接互相操作：

- 父组件通过输入将状态向下传递；
- 子组件通过事件将用户操作向上报告；
- 页面协调层统一保存当前的监控上下文；
- 各图表组件只关心自己收到的最新状态。

## 7. 监控类型切换时的配合

监控外壳统一管理三种视图：

| 监控类型   | 筛选视角        | 展示视角                                         |
| ---------- | --------------- | ------------------------------------------------ |
| 硬件监控   | 版本、Pod、容器 | CPU、内存、加速卡、网络和磁盘等资源情况          |
| 服务监控   | 版本、请求路径  | 请求量、成功率、错误和延迟等服务情况             |
| 大模型监控 | 版本、Pod       | 推理请求、队列、延迟、Token 和缓存等模型服务情况 |

切换监控类型时，页面协调层会同时切换：

1. 当前使用的筛选项定义；
2. 当前激活的监控展示组件；
3. 筛选结果对应的数据加载链路。

这保证了不同监控视图可以共用时间和页面布局，同时保持各自的筛选条件和展示内容。

## 8. 状态归属

为了理解组件之间的关系，可以按下表判断各类状态由谁负责。

| 状态                      | 主要负责层 |
| ------------------------- | ---------- |
| Predictor 业务信息        | 业务入口层 |
| 默认时间范围              | 业务入口层 |
| 当前监控类型              | 页面协调层 |
| 当前时间和查询步长        | 页面协调层 |
| 版本、Pod、容器等当前选择 | 筛选表单层 |
| 对外发布的完整筛选上下文  | 页面协调层 |
| 具体图表的展示状态        | 监控展示层 |

每个组件只保存自己完成职责所必需的状态，组件之间通过明确的输入和输出进行配合。

## 9. 整体结构总结

Predictor Monitor 可以归纳为一个分层的监控组件体系：

```text
业务数据
  → 转换为页面配置
  → 建立监控外壳
  → 建立筛选状态
  → 生成完整监控上下文
  → 交给具体监控组件
  → 展示对应数据
```

其中最重要的组件协作原则是：

1. 业务入口层只负责把 Predictor 转换为监控页面需要的信息；
2. 页面协调层是筛选组件与图表组件之间的桥梁；
3. 筛选组件通过响应式表单持续产生监控条件；
4. 监控展示组件只根据当前上下文加载和展示数据；
5. 用户操作向上传递，新状态再由协调层向下传播。

因此，虽然页面中存在大量图表和异步数据，但其宏观主线可以简化为：

> Predictor 提供业务上下文，筛选器产生查询上下文，监控外壳协调状态，具体图表消费这些状态。
