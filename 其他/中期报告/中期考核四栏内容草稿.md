## 二、拟解决问题描述

大模型推理服务的延迟违约可能来自三个不同层次：请求在 runtime 接纳处排队（并发上限不足）、GPU 算力被配额节流、或 ready 实例数不够。实际运行中瓶颈会随负载增长在三层之间迁移——同一尾延迟症状在不同阶段需要完全不同的处理动作，而调错层既浪费资源又修不好延迟。

现有系统各自只覆盖其中一到两层：autoscaler 调实例数、GPU 共享机制分算力、推理引擎管并发，三层的状态与参数分散在不同组件中，没有任何决策点能同时看到并修改它们；通用监控能发现服务变慢，却不能回答"该调哪一层、调到多少"。

本课题拟解决的具体问题：

1. **层次判断问题**：如何从运行时信号（队列增长、running 接近 MRR、kernel 配额等待、SLO 违约等）组合出可靠的层次压力证据，区分瓶颈当前位于哪一层；证据缺失或相互矛盾时系统应保守 HOLD 而非强行归类。
2. **目标配置问题**：判断层次只给出方向，"调到多少"需要实测响应面支撑；响应面只对测过的 workload 与档位有效，超出范围必须识别失配并回退保守策略。
3. **安全执行问题**：三类动作代价不同且非对称（配额可热切换、MRR 调整需重启引擎造成数十秒服务空窗、扩容需等待实例就绪），控制器需按代价选择足够配置、对每次动作做生命周期审计，并防止动作后瞬态引发的振荡。

## 三、已实际完成工作描述

1. **动机实验**：在 7B/L40S workload 上完成背景刻画实验，实测服务容量随配置迁移（MRR=1 时约 1.17 requests/s，提高 MRR 后约 13.3，再增一实例约 24.5），验证了"瓶颈随负载跨层迁移、单层调节可能无效"的研究动机。
2. **配置测量**：完成两条独立测量路径——CUDA MPS×MRR 5×4 网格（验证并发与算力的互补结构，网格内实测吞吐相差约 4.7 倍）；RCKM 配额×MRR 45 格响应面（Qwen2-7B/L40S、4096-token prompt、512-token output、cache 开启），产出容量下界、边界 TTFT p95 与配额等待证据，供控制器在线查表。
3. **系统实现**：在 dilu-pro 仓库中实现 CISB 控制器——诊断层将 runtime 与 GPU 日志归约为固定窗口的结构化证据（队列/running/quota wait 等 9 个字段）；策略层估计目标容量、检查 profile 适用性并输出带层次与目标值的结构化动作（ActionIntent）；执行层实现三个动作通道（RCKM 配额热切换、MRR replacement 生命周期 drain→stop→start→ready→resume、实例扩缩容生命周期核对）；反馈层持久化 settling/evaluation/cooldown 三窗状态与回滚计划，控制器重启后可恢复。
4. **在线实验验证**：
   - 三类单瓶颈场景五策略（Static/Quota-only/MRR-only/Instance-only/Full）消融，量化错层代价并验证组合控制器在单瓶颈场景不劣于专用单层策略；
   - 诊断证据场景级审计：264 个归档窗口中 146 个带标签窗口的支持类 macro-F1 达 0.920，数据缺失时正确返回 UNKNOWN 而非误判；
   - runtime→instance 迁移轨迹三轮重复：Full 依次完成 MRR 16→128 与实例 1→2 的组合动作链，三轮最终 post 均达成双 SLO；
   - 安全性测试：profile-shift 场景（8192-token prompt 超出测量条件）下 17/17 条记录保守 HOLD，无不安全动作。
5. **证据管理体系**：建立 claim-ledger 审计机制，逐条登记论文主张的证据状态（SUPPORTED-LIMITED / PARTIAL / UNSUPPORTED），明确"已验证什么、不能宣称什么"，保证论文结论不越界。
6. **论文撰写**：完成中英双语初稿（draft-v2），形成"量化错层代价→跨层统一控制对象→有界动作链与可审计代价"的完整叙事。
