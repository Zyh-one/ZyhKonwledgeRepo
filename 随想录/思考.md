* agent memory和KVCache；agent（codex，claude）在处理一个任务时，其实经常都是一个一个**会话**进行处理，而不会是一个请求对应一个任务；

  * 一个会话，一般会包含多个相关的请求（Prompt）
  * agent harness层面会将整个上下文history保存下来（可能是redis或其他存储体系）
  * 进来一个prompt，agent就会将prompt + history打包发送给vLLM推理实例
    * agent一般不会对history进行全量保存，可能会修改history中的无关信息，但是这依旧会提升prefixCache命中率
  * vLLM推理实例在接收到后的PrefixCache的命中率应该会特别高，因为之前的history处理过
  * **所以关键点来了**，在集群调度上，这些请求必须尽量被路由到保存着对应 prefix KV 的实例，并且该 KV 尚未被 eviction。
  * 此时就出现了一个“**隐形亲和性限制**”：同一个会话的后续请求，需要尽可能路由到一个Pod上，因为该Pod保留着前面历史对应的 Prefix KV Cache
  * 结论：这里出现一个“trade-off”，感觉是可以研究和讨论的重点
    * 考虑在KVCache调度上，可以做一些灵活处理和研究（AiBrix，MoonCake）
    * Context Compression
* 结合上一点的分析，发现Prefix-Cache也有“trade-off”的点（**Cache不是免费的**）

  ```
  命中率低
    ↓
  大量重复 Prefill
    ↓
  GPU 算力浪费、TTFT 上升
  ━━━━━━━━━━━━━━━━━━
          理想区域
  高复用 + 可接受 KV 占用
  ━━━━━━━━━━━━━━━━━━
    ↓
  为了继续提高命中率
  保留大量低价值 KV
    ↓
  KV Cache 压力 / eviction / load imbalance
  ```
