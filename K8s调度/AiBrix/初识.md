# 1.背景

- AiBrix是一个面向大规模 LLM 推理服务的云原生控制平面 / 系统编排层，而非单纯的推理框架
	- k8s集群   --->  AiBrix  ---> vllm,Sglang等推理引擎
	- 如何理解“云原生”？（我不是第一次听说“云原生”这个词汇，我目前对“云原生”的联想就是k8s，docker，Go语言等，但是我始终无法解释什么是“云原生”）
		- “应用应该如何被构建、部署、运行、扩缩容和治理”的系统设计思想，**管理维护运行中的应用服务**；非某具体技术
		- 特性：标准化，自动化，可声明（告诉系统“我希望始终有 2 个健康的模型实例在运行。”，系统自动维护）
		- 产生原因：只有在**分布式、多服务器、微服务背景**下，才会强烈出现自动管理应用服务的需求，因此产生了云原生概念。
		- 思考：
			- 在分布式，微服务的背景下，K8s 的出现，是为了通用地管理大规模容器化应用，比如各种web微服务，微服务中间件（redis，mysql）等。
			- 由于AI模型的参数量和服务体量不断增长，并且具备强烈的专用特性（KV Cache，请求形态等），此时单靠K8s管理还不够，故AiBrix应运而生。


# 开发K8s组件

- 我认为开发AiBrix等庞大K8s组件和开发一个简单的k8s调度器的基本流程是一样的
	- 所以，我打算先用kind虚拟环境去简单设计一个k8s调度器，来熟悉一下开发范式
- 开发范式：
```
声明期望状态
  ↓
API Server 保存状态
  ↓
组件监听资源变化
  ↓
组件根据当前状态做决策
  ↓
修改 K8s 对象或外部系统
  ↓
让实际状态逐渐靠近期望状态	
```

	- 该开发范式也体现出了“云原生”概念

- AiBrix，Volcano是如何和K8s进行集成的？
	- AiBrix和Volcano的安装和部署都是以“kubectl apply -f/-k xxx.yaml”所进行的
		- 所以我们可以把Volcano，AiBrix理解为**特定nameSpace中的一组服务**（若干Pod/Service/Deployment）
		- 同时，他们又不仅仅是普通服务，它们还会向整个集群注册CRD，ClusterRole，Webhook等就**集群级能力**
	- AiBrix和Volcano：
		- 运行形态上是普通服务
		- 能力上又具备集群级别的能力
		- 所以，它们是介于普通服务和K8s之间的扩展控制面组件
