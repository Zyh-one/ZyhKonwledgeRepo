- 将KubePlay的前期工作和此前使用k8s的相关经验结合，我这边对k8s的整体服务简单进行一个“分层”，大致分为三层：
	- 第一层（k8s原生控制面和基础组件）
		- 我对这一层的定位是“k8s自己的内置服务和资源”，其中大致包含kube-system命名空间中的相关核心组件，以及一些非k8s形式，非namespcae形态的服务（宿主机系统进程kubelet）
		- **补充**：
			- k8s原生控制面不是只包含在kube-system命名空间中，在这一点上，需要和下面的组件进行区分
	- 第二层（Volcano,AiBrix,Hami等k8s扩展控制系统）
		- 以**普通k8s服务**形式运行在集群中，比如volcano-system命名空间下的相关资源
		- 又通过RBAC，Controller等机制获得**集群控制级别**的能力，比如Volcano可以做一些批调度，Job调度等
	- 第三层（普通业务服务）
		- 这一层的pod**被K8s调度**，管理，重启等，就是最常见的业务工作负载，比如Nginx，数据库等

- 简单对开发Volcano，AiBrix这种K8s扩展系统的开发范式进行一个简单梳理
	- **存在形式**为普通K8s服务，比如deployment和daemonSet等
		- 故开发范式肯定包含：
			- 打包image镜像
			- 构造yaml配置文件
			- 执行kube apply -f 等命令
			- 实现在特定nameSpace启动服务的目的
	- **能力上**又具备集群控制级别的相关能力，我认为这部分得对应**镜像内部业务逻辑**，实际上大概率就是开发go代码的逻辑，因为go项目代码会被打包为image镜像
		- 同时，为了获取集群级别控制能力，除了利用go语言开发调度逻辑以外，还得配合权限配置，以获取全局的K8s集群状态，从而为后续的调度提供支持和原始参考信息
			- 在进行“调度”等集群控制级别的操作上，肯定需要用go语言去**调K8s的相关API**，故需要提前配置相关权限
				- 有点儿像在NIVDIA GPU写一个自定义算子，需要去调取CUDA Driver或CUDA Runtim等API一样 


- K8s调度器：
	- 在k8s中，没有一个原生K8s资源叫“调度器”，那么如何定义“调度器”？
	- 它是调度器，不是因为它是一个pod，而是因为它**内部image或内部进程**实现调度逻辑，并拥有调度权限
		- 也就是说，是不是调度器，是由“它干什么”决定的，而不由“它是什么”所决定
	- 既然“调度器”的概念突出在其业务逻辑上，而非存在形态上，那么其实也就存在一个**共同逻辑或流程**来开发“调度器”：
		```
		监听 Kubernetes API
			-> 缓存/理解集群当前状态
			-> 找出自己关心的对象
			-> 根据目标做决策
			-> 调用 Kubernetes API 写回结果
		```
