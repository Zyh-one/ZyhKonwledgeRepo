# 系统论文的创新：从“复杂技术”到“正确问题”

## 1. 一个越来越清晰的认识

在阅读 vLLM、SGLang、DistServe 这类系统工作时，我逐渐发现：

> 很多真正有影响力的系统创新，事后看来并没有难到不可理解。  
> 真正困难的地方，不一定是提出一个极其复杂的算法，而是能否在正确的时间点，看到一个被大家默认接受、但其实值得重新审视的问题。

这类工作的核心价值，往往不是“复杂”，而是：

- 问题抓得准；
- 抽象方式发生了变化；
- 新抽象足够简单；
- 但它能够打开一个新的系统设计空间；
- 最终通过完整系统实现，带来明显的性能、成本或可扩展性收益。

因此，系统研究中的“研究嗅觉”可能比单纯追求复杂度更加重要。

---

## 2. 为什么很多经典创新事后看起来都很自然？

### 2.1 vLLM / PagedAttention

最核心的问题可以简化为：

> LLM 推理中的 KV Cache 长度动态变化，连续显存分配会带来碎片和浪费。

然后重新思考：

> 操作系统早就通过 Paging 解决过“逻辑连续、物理不连续”的内存管理问题，那么 KV Cache 为什么不能采用类似思想？

于是：

```text
原来的抽象：
KV Cache = 一整块连续 Tensor

新的抽象：
KV Cache = 一组可以分页管理的 Block / Page
```

PagedAttention 的价值，不只是“实现了某个复杂 Kernel”，而是改变了我们看待 KV Cache 内存管理的方式。

---

### 2.2 SGLang / RadixAttention

另一个非常直观的问题：

```text
Request A:
System Prompt + Shared Prefix + Question A

Request B:
System Prompt + Shared Prefix + Question B
```

既然两个请求拥有很长的相同 Prefix，那么：

> 为什么已经计算过的 Prefix KV Cache 还要重新计算？

于是把请求的 KV Cache 从：

```text
每个 Request 完全独立
```

重新抽象成：

```text
具有共享前缀结构的一组对象
        ↓
      Radix Tree
```

从而实现跨请求 Prefix KV Cache 的自动复用。

同样，一旦别人把这个思想讲出来，会产生一种：

> “对啊，为什么不这么做？”

的感觉。

---

### 2.3 DistServe / Prefill-Decode 分离

DistServe 最核心的观察同样很容易理解：

LLM 推理的两个阶段，本质上具有完全不同的计算特征。

```text
Prefill
- 大矩阵计算
- 并行度高
- 更偏 Compute-bound
- TTFT 重要

Decode
- 每轮生成少量 Token
- 访存压力突出
- 更偏 Memory-bandwidth-bound
- TPOT / ITL 重要
```

于是产生一个非常自然的问题：

> 既然 Prefill 和 Decode 是两种不同的 Workload，为什么一定要把它们绑定在同一组 GPU 上执行？

进一步得到：

```text
原来的抽象：
一个请求 = 在同一个实例上完成 Prefill + Decode

新的抽象：
一个请求 = Prefill Workload + Decode Workload
                    ↓
             可以独立部署和调度
```

这一步看似简单，却打开了：

- 独立扩缩容；
- 不同并行策略；
- 不同 GPU 配置；
- 独立 SLO 优化；
- Prefill / Decode 比例优化；
- KV Cache Transfer；

等大量新的系统设计空间。

---

## 3. 这些工作的共同点：重新定义原来的对象

把几个例子放在一起，可以发现一种非常漂亮的共同结构。

### PagedAttention

```text
KV Cache
   ↓
不再视为连续大块 Tensor
   ↓
视为 Pages / Blocks
```

### RadixAttention

```text
不同请求的 KV Cache
   ↓
不再视为完全独立
   ↓
视为具有共享 Prefix 的树结构
```

### DistServe

```text
LLM Request
   ↓
不再视为统一 Workload
   ↓
视为 Prefill + Decode 两种不同 Workload
```

因此，一个重要认识是：

> 很多系统创新的核心，并不是“发明了一个复杂东西”，而是“换了一种方式看原来的东西”。

也可以理解为：

> **找到一个更正确的抽象。**

---

## 4. 顶级系统研究常见的问题结构

很多优秀系统工作，都可以压缩成下面这条链路：

```text
观察真实系统
      ↓
发现主要性能瓶颈
      ↓
找到瓶颈背后的结构性原因
      ↓
质疑一个被默认接受的前提
      ↓
提出一个新的简单抽象
      ↓
重新设计系统
      ↓
完整实现
      ↓
实验验证：
性能 / SLO / 成本 / 可扩展性显著改善
```

其中最难、也最重要的地方通常不是最后写代码，而是：

```text
“到底哪个默认前提值得被打破？”
```

---

## 5. 一个值得长期训练的问题

以后阅读系统论文时，不应该只问：

> 这篇论文做了什么？

还应该问：

> **作者到底比别人早看见了什么？**

例如：

### PagedAttention

作者更早看见：

> KV Cache 的问题不仅是“占显存”，而是它的动态内存管理方式本身存在结构性浪费。

### RadixAttention

作者更早看见：

> 请求之间并不完全独立，Prefix 中存在大量可利用的共享结构。

### DistServe

作者更早看见：

> Prefill 和 Decode 不应该被看作同一种计算任务。

这个问题可能比直接记论文的算法流程更加重要。

---

## 6. “Idea 简单”不代表成果容易

这里需要特别警惕一种误解：

> Idea 一句话可以解释清楚 ≠ 论文很容易做。

实际上，优秀系统论文往往具有一个特点：

> **Idea 非常简洁，但 Implementation 非常深。**

### PagedAttention 真正落地还需要解决

- Block allocator；
- KV Cache manager；
- Scheduler 集成；
- Attention Kernel；
- Batch 管理；
- 显存管理；
- 并发请求；
- 模型兼容；
- CUDA 实现；
- Correctness；
- Production Serving；
- Benchmark。

### DistServe 真正落地还需要解决

- KV Cache Transfer；
- Prefill / Decode Placement；
- Parallelism Strategy；
- Resource Allocation；
- Scheduling；
- Goodput Modeling；
- TTFT / TPOT SLO；
- Workload Modeling；
- Cluster Evaluation；
- Fault Handling。

因此：

```text
优秀系统研究 ≠ 复杂 Idea

优秀系统研究 =
简单而关键的 Idea
+
深度系统实现
+
充分实验验证
```

## 7. 系统研究真正需要的“嗅觉”

这类创新往往需要三个条件同时出现。

### 7.1 问题已经足够痛

如果真实系统没有受到这个问题的严重影响，那么再漂亮的优化也没有太大意义。

例如随着 LLM Serving 规模增长：

```text
模型越来越大
上下文越来越长
KV Cache 越来越大
请求并发越来越高
SLO 越来越严格
```

新的瓶颈才逐渐变成真正值得研究的问题。

---

### 7.2 Workload 或硬件发生变化

很多新的系统问题，并不是旧系统设计“错了”，而是：

> 当时的设计基于当时的 Workload 是合理的，但现在 Workload 已经变化。

例如：

```text
以前：
模型权重可能是核心瓶颈

后来：
KV Cache、Decode Memory Bandwidth、
Prefix Reuse、Distributed KV Transfer
逐渐成为新的瓶颈
```

因此研究者必须不断重新观察系统。

---

### 7.3 正好有人站在真实系统旁边看到它

这也是工程经验的重要意义。

很多研究问题最早可能只是工程中的一句抱怨：

```text
“为什么 PD 配比这么难调？”

“为什么 GPU Utilization 很高，
但吞吐还是上不去？”

“为什么 Prefix Cache 明明已经存在，
路由层却不知道？”

“为什么 Scheduler 完全感知不到
KV Transfer 的成本？”

“为什么 K8s 只知道 GPU 数量，
却不知道 vLLM 内部真正的运行状态？”

“为什么所有 Workload
都使用同一种扩缩容策略？”
```

如果只是修掉当前 Bug，这些只是工程问题。

但如果继续追问：

> 为什么这个问题会反复出现？

> 它是不是某个系统抽象本身有问题？

那么工程问题就可能逐渐演化成研究问题。

---

## 8. 系统论文可能从“不爽感”开始

一个值得长期保留的研究习惯是：

> 不要忽略真实系统中反复出现的“不爽感”。

因为它可能意味着：

```text
反复出现的工程问题
        ↓
某种结构性瓶颈
        ↓
现有设计中的默认假设
        ↓
这个假设可能已经不成立
        ↓
新的研究机会
```

很多优秀论文的起点，本质上可能就是：

> “这个设计真的合理吗？为什么所有人都默认这么做？”

---

## 9. 我更想追求什么样的论文？

我并不一定需要追求：

> 一个别人第一眼完全无法理解、数学上极其复杂的创新。

我真正想追求的可能是这种成果：

> 我观察到现有系统普遍默认 X。

> 但在新的 Workload / Hardware / Scale 下，X 已经不再成立。

> 因此我把系统重新抽象成 Y。

> 基于 Y 重新设计和实现系统。

> 最终在真实 Workload 下显著改善性能、成本或者 SLO。

理想情况下，别人听完核心 Idea 后会说：

> **“好像确实应该这样。”**

而看到实验结果以后会意识到：

> **“但以前大家真的没有这么做。”**

这种工作往往具有很强的系统研究美感。

---

## 10. 博士阶段真正值得培养的能力

如果未来希望做出 vLLM、SGLang、DistServe 这类系统成果，我认为需要逐渐培养的并不只是论文写作能力，而是：

### ① 对真实系统足够熟悉

能够真正理解：

- vLLM / SGLang；
- Scheduler；
- KV Cache；
- GPU / MLU；
- PD 分离；
- Distributed KV；
- Gateway / Routing；
- Kubernetes；
- Cluster Scheduling；
- Metrics / SLO。

---

### ② 能从指标发现异常

不仅知道：

```text
TTFT
TPOT
Throughput
GPU Utilization
```

还需要理解：

```text
指标为什么变化？
指标由哪些系统阶段决定？
哪些指标之间存在因果关系？
```

---

### ③ 能追到瓶颈的根因

从：

```text
“性能不好”
```

追到：

```text
哪个阶段？
哪个资源？
哪个 Scheduler Decision？
哪个数据移动？
哪个系统假设？
```

---

### ④ 能区分“工程 Bug”和“研究问题”

工程 Bug：

```text
代码写错了
→ 修掉即可
```

研究问题：

```text
代码没有写错
但系统设计本身在某种 Workload 下就不合理
```

后者才更可能产生真正有价值的论文。

---

### ⑤ 能找到新的系统抽象

这是最困难、也最核心的能力：

```text
现象
 ↓
规律
 ↓
结构性原因
 ↓
新的抽象
 ↓
新的系统设计
```

---

## 11. 一个值得长期使用的论文阅读模板

以后读系统论文，可以尝试固定回答下面这些问题。

### Problem

作者到底在解决什么真实问题？

### Observation

作者观察到了什么以前被忽略的现象？

### Assumption

现有系统默认了什么前提？

### Broken Assumption

作者发现哪个前提已经不成立？

### New Abstraction

作者如何重新定义这个问题？

### Mechanism

为了实现新抽象，设计了什么机制？

### Implementation

真正落地时最困难的工程问题是什么？

### Evaluation

最终改善了什么？

```text
Latency?
Throughput?
Goodput?
SLO?
Memory?
Cost?
Scalability?
```

### Research Taste

最后也是最重要的问题：

> **如果我当时也在维护这个系统，我有没有可能比作者更早意识到这个问题？**

---

## 12. 最终认识

系统研究真正迷人的地方可能就在于：

> 最好的 Idea 往往不是“复杂到没人能够理解”，而是“简单到别人听完以后觉得它本来就应该存在”。

但要做到这一点，需要长期积累：

```text
深入真实系统
      +
真实 Workload
      +
性能指标
      +
工程经验
      +
论文积累
      +
持续观察
      ↓
研究嗅觉
```

因此，工程能力和研究能力并不是冲突的。

对于 AI Infra / LLM Serving 这样的系统方向，深度工程实践甚至可能正是研究嗅觉的重要来源。

最终希望达到的状态不是：

> “我掌握了多少论文。”

而是：

> **当真实系统出现一个新的结构性问题时，我能够意识到：这里可能存在一个尚未被正确抽象的问题。**

这可能就是做出下一类 vLLM、SGLang、DistServe 式工作的起点。
