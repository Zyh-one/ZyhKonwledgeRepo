# 1. AiBrix的项目结构

梳理AiBrix的项目结构，提取项目理解入口

| 目录    | 作用                                                                         | 层次             |
| ------- | ---------------------------------------------------------------------------- | ---------------- |
| api/    | 定义 aiBrix 的 Kubernetes API，也就是 CRD 对应的 Go 类型                     | 理解 CRD 的入口  |
| cmd/    | 各个可执行程序的入口，即 Go 的`main` 包                                    | 分析程序启动入口 |
| config/ | Kubernetes/Kustomize 配置，包括 CRD、RBAC、Controller Deployment、Gateway 等 | 连接源码与部署   |
| pkg/    | Controller、Gateway 插件、缓存、客户端等主要 Go 实现                         | 最核心的业务代码 |
| python/ | Python 运行时与 KV Cache 实现，包括部分 C++/CUDA 扩展                        | 数据面核心代码   |

核心代码文件夹，后续围绕以上文件夹对AiBrix进行剖析

其他附属文件夹

* `benchmarks/`：压测客户端、工作负载生成及 autoscaling、gateway、KV cache、LoRA 等场景测试
* `build/`：构建容器镜像需要的 Dockerfile
* `deployment/`：面向具体环境的完整部署方案，如 Cambricon、Docker Compose、Terraform
* `development/`：开发环境、教程、实验配置和本地调试材料
* `dist/`：对外发布的制品，目前主要是 Helm Chart
* `hack/`：代码生成、校验、发布等开发脚本
* `observability/`：Grafana Dashboard、Prometheus ServiceMonitor 等可观测性配置
* `samples/`：各种功能的示例 YAML，例如 autoscaling、LoRA、分布式推理、KV cache
* `scripts/`：各种辅助脚本
* `test/`：测试（集成测试，E2E测试，回归测试，测试工具）

主要实现位于：`pkg/plugins/gateway/`

### 1.2.3 Kvcache-watcher

KvCache-Watcher只在部署了“独立的分布式 KV Cache服务”时起作用，它负责告诉缓存客户端（实际存储KVCache的Pod）：当前有哪些缓存服务器（使用KVCache的推理实例），以及每份 KV数据应该访问哪个服务器。

使用条件：

* 部署了 AiBrix `KVCache` CR；
* 创建了多个 KVCache Server Pod；

KVCache Pod：由KVCache CR创建的独立分布式缓存服务节点，区别于vLLM实例Pod；这些是专门存储，或共享 KV Cache数据的服务 Pod，比如`HPKV Pod`，`InfiniStore Pod`，`Vineyard Pod`；vLLM原生适配的MoonCake Store其实也可以放入这一层次

补充：什么是HPKV，InfiniStore，Vineyard？

答：它们都是独立的KV Cache存储/共享后端

* Vineyard：分布式内存数据管理系统，最初并非为LLM KV Cache所做
* HPKV：KV Cache backend，KVCache专用的

具体使用场景：

最初存在两个缓存节点：

```
cache-pod-0: 10.0.0.10
cache-pod-1: 10.0.0.11
```

kvCache-watcher通过k8s informer监听这些Pod：

```
watch Pods
    ↓
筛选role=cache且属于指定KVCache实例的Pod
    ↓
提取Pod IP、RDMA IP和端口
    ↓
建立一致性哈希环
    ↓
计算每个节点负责的Slot
    ↓
把节点拓扑写入Redis
```

Redis中的逻辑信息可能类似：

```
{
  "version": 1,
  "nodes": [
    {
      "name": "cache-pod-0",
      "addr": "10.0.0.10",
      "port": 18512,
      "slots": [{"start": 0, "end": 2047}]
    },
    {
      "name": "cache-pod-1",
      "addr": "10.0.0.11",
      "port": 18512,
      "slots": [{"start": 2048, "end": 4095}]
    }
  ]
}
```

**实际作用：**缓存客户端需要存取某份 KV Cache时

```
KV Cache Key
    ↓ hash
得到Slot 3000
    ↓ 查询拓扑
Slot 3000属于cache-pod-1
    ↓
访问10.0.0.11:18512
```

**实际作用**：后期维护，当KVCache Pod发生变化时，KvCache-watcher需要进行维护，保证缓存客户端的正常使用

目前的实际场景：

* **PD分离（最重要）**
* KV Cache从 GPU显存卸载到远端缓存（LMCache）
* 多个推理实例共享 Prompt Prefix Cache；
* 请求被调度到不同 Pod后复用已有 KV Cache；
* KV Cache容量横向扩展；
* .....

核心逻辑对应于：`pkg/kvcache-watcher`，其中大致包含：

* Pod Informer；
* workqueue；
* 节点发现；
* 一致性哈希；
* Slot分配；

区别于`pkg/cache/kvcache`

## 1.3 pkg

主要GO业务实现；

内部代码十分多，前期只需要关注重点模块

### 1.3.1 controller

多种调谐逻辑；

* `podautoscaler`：当前副本数是否符合扩缩容计算结果；
* `modeladapter`：用户声明的 LoRA Adapter 是否已经加载到推理 Pod；
* `kvcache`：KV Cache 服务节点是否符合 CR 中的声明；
* `stormservice`：RoleSet、PodSet、Pod、Service 是否符合编排要求；
* `rayclusterfleet`：Ray 集群数量和状态是否符合期望。

问：关于controller的逻辑，可以沿着这几条线路进行梳理吗？

k8s的调谐循环

```
用户提交 CR
    ↓
Controller Watch 到变化
    ↓
读取 Spec
    ↓
检查 Deployment、Pod、Service 等实际状态
    ↓
创建、更新或删除下层资源
    ↓
更新 CR 的 Status
    ↓
等待下一次事件
```

### 1.3.2 client

CRD 自动生成的客户端代码；Controller

* `clientset`：读取和修改 aiBrix CR；
* `informers`：高效监听资源；
* `listers`：从本地缓存查询资源；
* `applyconfiguration`：支持 Server-Side Apply。

作用：aiBrix 程序用来访问 Kubernetes API Server、操作 aiBrix 自定义资源

问：如何理解这里的客户端？k8s中的客户端是什么？

客户端：aiBrix controller，从 Kubernetes API Server 的角度

AiBrix controller会查询或修改自己的CRD，此时它需要通过pkg/client中的相关函数请求K8s  API  Server

比如

```Go
client.AutoscalingV1alpha1().PodAutoscalers(namespace).Get(ctx, name, options)
//向 Kubernetes API Server 查询某个 namespace 下的 PodAutoscaler
```

pkg/client包括：

* `clientset/`：直接对 CR 进行增删改查；
* `informers/`：持续监听资源变化，并建立本地缓存；
* `listers/`：从 Informer 的本地缓存中快速查询资源；
* `applyconfiguration/`：构造 Server-Side Apply 所需的数据。

## 1.5 python

aibrix和aibrix_kvcache

**控制面和数据面（这部分暂时放这儿，整理好后，可以放到前面）**

控制面负责“决定应该怎么运行”，比如启动几个推理副本，某个 LoRA Adapter 应该加载到哪个 Pod等等

数据面真正处理业务数据，比如用户的 prompt，Token，模型权重；

Gateway（网关）算控制面，还是数据面？

* “控制面/数据面”划分的是**职责**，不完全等于某种语言或某个目录
* Gateway 的配置、后端发现、策略管理偏控制面；Gateway 转发每一个真实推理请求的过程属于数据面。

yaml整体生命周期：

```
api/ 中定义 Go 类型
        ↓ 代码/清单生成
config/crd/ 中生成 CRD YAML
        ↓ 注册到 Kubernetes
config/ 中安装 Controller、RBAC、Gateway 等
        ↓ aiBrix 系统安装完成
samples/ 中创建具体推理业务
        ↓ Controller 调谐这些资源
development/ 中提供开发、模拟和教程环境
        ↓
test/、benchmarks/ 验证正确性和性能
        ↓
dist/ 打包为 Helm Chart 对外发布
        ↓

```

1. config/：描述 aiBrix 本身如何安装到 Kubernetes 中，既构建aibrix-system命名空间
   1. 注册crd资源：api/*_type.go  -----> config/crd/ *.yaml
   2. controller，gateway等组件的构建
2. samples/：业务场景yaml；**aiBrix 安装完成后**，用户如何利用它部署具体推理业务。
   1. 一个sample同时包含deployment，service等
3. development/：服务开发过程，比如部署模拟vLLM服务等
4. dist/：Helm chart；发布给用户

# 2. AiBrix项目部署模式

Yaml；Kustomize；Gitlab CI/CD

## 2.1 Gitlab-ci

整个AiBrix的部署流程：推送git tag；gitlab创建pipeline；pipeline根据规则执行相关job和阶段（发版，测试，更新等）

.gitlab-ci是部署流程的入口，声明4个阶段：

* test
* build
* release
* deploy

（标准的项目ci/cd流程）

补充：通常，项目中会同时存在`.gitlab-ci.yml`和`.gitlab-cd.yml`

* CI：测试、检查、构建镜像
* CD：将镜像或者 YAML 部署到运行环境

但Gitlab默认只识别一个入口 .gitlab-ci.yaml，可以同时包含ci/cd（当前项目）

**1. Test阶段**

执行make test-ci，make test-race-condition

make xxxx   --->  执行项目根目录MakeFile中的xxxx部分

```Shell
.PHONY: test-ci
test-ci: manifests generate fmt vet envtest ## Run CI tests for gateway plugins and controllers only.
	@echo "Running CI tests (gateway plugins + controllers)..."
	KUBEBUILDER_ASSETS="$(shell $(ENVTEST) use $(ENVTEST_K8S_VERSION) --bin-dir $(LOCALBIN) -p path)" \
	go test $$(go list ./... | grep -E '/pkg/plugins/gateway|/pkg/controller/') -coverprofile cover.out

.PHONY: test-race-condition
test-race-condition: manifests generate fmt vet envtest ## Run tests with race detection enabled.
	KUBEBUILDER_ASSETS="$(shell $(ENVTEST) use $(ENVTEST_K8S_VERSION) --bin-dir $(LOCALBIN) -p path)" go test -race $$(go list ./... | grep -v '/e2e\|/integration')
```

 以上为test阶段所执行的两段代码；go test

make test-ci：主要测试`pkg/plugins/gateway/`和`pkg/controller/` ；manifests；envtest

make test-race-condition：竞态检测go test -race .... ；goroutine

**阶段作用**：验证 controller 和 gateway-plugin 是否能够编译、通过静态检查、单元测试和并发安全检查。

**2.Release阶段**

生成镜像build Dockerfile；发布`controller-manager`和`gateway-plugins`组件

对应文件：`build/container/Dockerfile` / `build/container/Dockerfile.gateway`

每个组件构建两个CPU架构amd64/arm64，最终得到4个镜像

**3.Build阶段**

和release阶段一致，针对`controller-manager`和`gateway-plugins`组件，构建镜像

执行makefile中的相应部分进行docker build，并推送`10.3.68.2:5001/aibrix`内部仓库

核心区别在于使用场景不同

* release：正式离线交付，打包.tar；build：内部环境使用，推送镜像仓库

**4.deploy阶段**

部署AiBrix到内部K8s集群；`deployment/cambricon`；`kustomization.yaml`；

1. 替换镜像 Tag，修改`overlays/machine34/kustomization.yaml`
2. 服务端校验 AIBrix CRD

   ```
   kubectl apply --dry-run=server --server-side -k ./aibrix/crds
   ```
3. 服务端校验 Envoy 和 KubeRay CRD

   ```
   kubectl apply --dry-run=server --server-side -k ./envoy-gateway/crds
   ```
4. 部署主体资源

   ```
   kubectl apply --server-side --force-conflicts -k overlays/machine34/
   ```
